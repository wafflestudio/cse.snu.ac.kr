# 디자인 시스템 결정 기록

이 문서(`/design-system`)가 **무엇을 보여주는지**는 `-content.mdx` 에 있다. 여기엔 **왜 그렇게 정했는지**,
특히 기존 코드에서 바꾼 것과 그 이유를 적는다. 화면을 바꾼 결정은 되돌릴 근거가 남아 있어야 한다.

작업 방식은 **인터페이스 인벤토리 먼저**다(Brad Frost). 원칙을 먼저 쓰면 남의 시스템에서 베낀 일반론이
나온다. 실제로 무엇이 쓰이는지 세고, 거기서 이미 지켜지던 규칙을 발견해 이름을 붙인다.

## 색

### 중립색 11단계는 Tailwind 기본값이다

`app.css` 의 `--color-neutral-*` 11개가 Tailwind 의 `neutral` 척도와 **한 글자도 다르지 않다.**
즉 회색은 아무도 고른 적이 없다. 반면 앱 셸이 쓰던 색들은 척도와 푸른기가 일관돼 누군가 고른 값이었다.
**디자이너의 결정은 팔레트 밖에 있었고, 팔레트 안에는 프레임워크 기본값이 있었다.**

### `--color-shell-*` 을 추가했다

내비게이션·헤더·푸터가 하드코딩으로 쓰던 네 색을 토큰으로 들였다. 값은 그대로라 화면은 안 변했다.

```
shell-100  #323235  LNB 사이드바 · 모바일 내비 목록   z-50 (앞)
shell-200  #2d2d30  헤더
shell-300  #262728  푸터
shell-400  #1f2021  LNB·모바일 내비 상세 패널          z-40 (뒤)
```

중립색과 달리 **푸른기가 2~3 섞여 있고, 명도가 깊이를 뜻한다** — 밝을수록 앞, 어두울수록 뒤.
사이드바(z-50)가 상세 패널(z-40)보다 밝은 게 우연이 아니다.

### `neutral-75` 는 지웠고 `neutral-850` 은 되돌렸다

둘 다 실사용이 한 파일뿐이라 이웃으로 합쳤는데, **`neutral-850` 은 되돌렸다.**
합치고 나서 카테고리 페이지를 보니 제목 영역과 카드 영역이 한 덩어리가 돼 있었다.
원래는 제목 영역만 `neutral-850`(#1e1e1e)이고 그 아래 카드 영역은 `neutral-900`(#171717) 이라,
**제목 영역이 한 단계 앞으로 나와 있었다** — 셸의 "명도가 깊이"와 같은 규칙이다.
값이 8/255 차이라 나란히 안 놓으면 안 보이는데, 그 페이지에서는 나란히 놓인다.

```
neutral-75  → neutral-100   학사 일정 타임라인의 본문 패널 2곳    (합침)
neutral-850                 카테고리 페이지 제목 영역 1곳         (되돌림)
```

어두운 쪽 면은 이제 세 단계다 — `neutral-900`(바탕) · `neutral-850`(제목 영역) · `neutral-800`(그 위의 카드).

합칠 이웃은 **역할**로 정했다. 기존 사용처를 보니 아무도 안 적었지만 지켜지던 규칙이 있었다:

```
neutral-50    폼 입력 배경 · 파일 목록      입력하는 면
neutral-100   본문 패널 · 안내 박스 · 카드   읽는 면
neutral-900   제목 띠 · 페이지 배경         어두운 틀
```

### 메인 공지 카드는 `shell-400` 이 아니라 `neutral-800` 이다

`NoticeSection` 의 `#212121`(카드)·`#202020`(태그 pill)은 색값만 보면 `shell-400`(#1f2021)이 가장
가까웠다(거리 2.2 대 `neutral-800` 8.7). 그래서 셸 계열로 흡수했는데 **화면에서 바로 티가 났다.**

카드가 놓인 배경이 `neutral-900` **순수 중성**이기 때문이다. 푸른기 있는 면을 중성 배경 위에 놓으면
색 틀어짐이 드러난다. 셸의 푸른기가 티나지 않는 건 셸끼리 인접해 계열이 일관되기 때문이다.

> **계열을 가르는 건 색값의 거리가 아니라 무엇 옆에 놓이느냐다.**

그래서 `neutral-800` 으로 갔다. 원래보다 5 밝아 카드가 배경에서 조금 더 도드라진다(배경 대비 +10 → +15).

### 주황을 역할 이름으로 바꾸고 상태색을 정의했다

`main-orange-dark` 가 두 가지 일을 겸하고 있었다 — 10곳은 **메인 화면의 정적 색**(어두운 배경 위에서
한 단계 죽인 주황), 3곳은 **hover 색**. 이름이 용도를 말하지 않으니 `CategoryGrid` 에서
`hoverColor` 에 기본 배경색을 넣는 식의 혼동이 생겼다.

```
main-orange         #ff6914   기본 강조
main-orange-muted   #e65817   어두운 배경 위의 주황 (구 -dark, 13곳 이름 변경)
main-orange-hover   #ff7b34   ← 새로 정의. ImageModal 이 직접 만들어 쓰던 값
main-orange-active  #f55a00   ← 같음
반투명은 main-orange/80       ← #ff6914cc 와 컴파일 결과가 동일
```

`#e65615`(새소식 섹션·캐러셀 2곳)는 `#e65817` 의 근접 오타로 보고 `muted` 로 합쳤다. 화면상 구분 불가.

### 회색은 줄이는 게 아니라 이름을 붙이는 것이었다

`neutral-600` 을 놓고 "지울까"를 고민하다 방향이 틀렸다는 걸 알았다. 다른 시스템들은 회색을 줄이지 않는다
— [Radix Colors](https://www.radix-ui.com/colors/docs/palette-composition/understanding-the-scale)는 12단계,
Carbon 10단계, Material 3 은 13단계다. 우리(11)와 비슷하거나 많다.

차이는 **개수가 아니라 이름**이다. Radix 는 12단계 각각에 용도를 못박아 두고(1 앱 배경 … 11 저명도 텍스트,
12 고명도 텍스트), Atlassian·Polaris·Carbon 은 원시 팔레트 위에 `color.background.brand.bold` 같은
**의미 층**을 따로 쌓는다. 우리에게 없던 건 값이 아니라 그 이름이었다.

그래서 `neutral-75` 를 지운 건 여전히 옳다(**역할이 없어서** 이름도 못 붙였다). `neutral-850` 은
반대였다 — 역할이 있는데 내가 못 읽었다. 나머지도 지울 대상이 아니라 역할을 찾을 대상이었다.

### 글자색 여섯을 다섯 역할로 정리했다

시작할 때 400·500·600·700·800·950 여섯이 기준 없이 섞여 있었다. 인벤토리로 각자 하는 일을 확인하고
역할이 겹치는 것만 합쳤다.

```
neutral-950   주황 면 위의 글자 (대비상 필수)
neutral-800   본문 · 제목 (body 기본값)
neutral-600   선택 컨트롤 레이블 (체크박스·라디오)
neutral-500   본문 옆 보조 설명
neutral-400   표·목록의 부수 정보 · 비활성 상태
neutral-700   글자색에서 제외 — 어두운 면 전용(Button neutral variant·구분선)
```

**`neutral-700` 은 없앤 게 아니라 좁혔다.** 글자로 쓰인 13곳은 역할이 제각각이었고(같은 h4 소제목이
한 곳은 700, 다른 곳은 800), 전부 본문(800)으로 옮겼다. 남은 5곳은 버튼 배경·구분선·hover 로,
"어두운 면"이라는 분명한 역할이 있다.

**본문 기본값을 950에서 800으로 내렸다.** `__root` 가 body 를 950으로 깔았지만 실제 본문은 44곳이
800을 명시하고 있었다 — 기본값이 기본이 아니었다. 다수에 맞췄다.

### 주황 면 위에서는 `neutral-950` 이어야 한다

본문 기본값을 800으로 내리면서 메인 **중요 안내** 카드의 대비를 깨뜨렸다가 되돌렸다.

```
bg-main-orange-muted (#e65817) 위
  neutral-950  5.44   본문 기준(4.5) 통과
  neutral-800  4.16   미달
  white        3.64   미달
```

흰색도 800도 못 넘기는 자리라 **어두운 글자가 선택이 아니라 필수**고, 950만 통과한다.
지우려던 색에 역할이 있었던 셈이다. 해당 위치는 `ImportantSection`(제목·본문 4곳)과
`NoticeSection` 의 선택된 태그 pill.

### 팔레트를 닫았다

`@theme` 에 `--color-*: initial` 을 넣어 Tailwind 기본 팔레트를 껐다. [공식 문서가 권하는 방법](https://tailwindcss.com/docs/colors)이고,
이제 `bg-rose-400` 같은 건 **클래스 자체가 생성되지 않는다**. 그 전까지는 우리가 얹은 20개 말고도
기본 22계열이 전부 살아 있었고, `text-red-600` 이 유일한 이탈이었던 건 규칙이 막아서가 아니라
아무도 안 썼기 때문이었다.

닫으면서 `white`·`transparent`·`inherit` 은 직접 선언했다(기본에 기대고 있던 것들). CSS 153K → 144K.

⚠️ **임의값 문법(`text-[#f5f5f5]`)은 여전히 통과한다.** `--color-*: initial` 은 이름 있는 클래스만 막는다.
현재 앱 코드에 그런 값은 0개지만(메인 그래픽 제외), 막으려면 린트 규칙이 따로 필요하다.

### 오류색을 팔레트에 들였다

오류를 표현하는 자리가 셋인데 셋이 다 달랐다 — 폼 검증은 `text-red-600`, 토스트는 sonner 기본값,
전체 에러 화면(404)은 `main-orange`. 마지막은 화면 전체 상태라 브랜드 색을 쓰는 게 자연스럽고,
토스트는 벤더링한 라이브러리 값이라 건드리지 않았다. 폼 검증만 `--color-error` 로 옮겼다.
값은 Tailwind red-600 그대로라 화면은 안 변한다.

### 오타 셋과 죽은 자산을 정리했다

토큰과 SVG·CSS 의 연결이 끊겨 있는 틈으로 실제로 값이 새어 있었다.

```
#E65615  →  #e65817   small_right_arrow.svg. main-orange-muted 의 근접 오타
#1E1E1E  →  #171717   down_arrow.svg. 메인의 neutral-900 바탕 위인데 neutral-850 값이 박혀 있었다
삭제                  routes/$locale/assets/small_right_arrow.svg — 아무도 안 쓰는 사본
```

### 투명도에 역할이 하나 있었다

`rgba()` 22곳을 보니 하나만 토큰감이었다. `Dialog`·`AlertDialog`·`ImageModal` 세 파일이 **같은
`rgba(0,0,0,0.5)` 를 따로 적고 있었다** — 역할이 같고 값도 같다. `--color-overlay` 로 묶었다.

나머지 13곳은 전부 **그림자**인데 투명도가 0.05·0.07·0.15·0.2·0.25·0.3 여섯 가지다. 하나로 묶으려면
그림자 체계를 새로 정해야 해서 색 작업이 아니라 별도 인벤토리로 넘겼다.

푸터 하단의 `rgb(30,30,30)` 은 셸 척도로 편입했다(`shell-400`). 밝기 30 대 31 로 사실상 같고,
푸터 윗부분이 이미 `shell-300` 이라 계열이 맞는다. 메인 공지 카드와 반대 경우다 —
거기선 주변이 중성이라 푸른기가 튀었지만, 여기는 주변이 전부 셸이다.

### `background.svg` 의 `#1b1b1b` 60곳은 그대로 둔다

메인 배경 패턴이다. `neutral-900`(#171717) 바탕보다 **4 만큼만 밝아야** 패턴이 드러나는데 척도에
그 단계가 없다. 게다가 `url()` 로 부르는 SVG 라 `currentColor` 도 토큰도 못 읽는다 — 인라인 `<svg>`
로 바꾸면 두 사용처가 문서에 13.4KB 를 얹어서 그것도 안 된다. `app.css` 에 이유를 적어뒀다.

### E2E 는 색 변화를 못 잡는다

오늘 색을 전역으로 바꿨는데 스냅샷 116장이 하나도 안 깨졌다. `playwright.config.ts` 에 스크린샷
옵션이 없어 [기본값 `threshold: 0.2`](https://playwright.dev/docs/test-snapshots)(YIQ 색공간의
픽셀당 허용 색차)가 적용되기 때문이다.

```
neutral-700 → 800   차이 0.10
neutral-950 → 800   차이 0.06     모두 0.2 미만 → 통과
```

`apps/web/CLAUDE.md` 가 "픽셀 회귀는 E2E 소유"라고 적어뒀지만 **색에 대해서는 그 소유권이 비어 있다.**
`expect.toHaveScreenshot.threshold` 를 낮추면 잡히지만 폰트 안티에일리어싱으로 플레이키해질
위험이 있어 한 번 재보고 정할 일이다.

## 타이포그래피

### 굵기 넷 중 둘이 같은 일을 하고 있었다

`font-normal` 74 · `font-medium` 52 · `font-semibold` 28 · `font-bold` 42.
Pretendard Variable(`font-weight: 45 920`)이라 넷 다 실제로 다르게 그려진다 — 폴백으로 뭉개진 게 아니다.

역할을 세어 보니 **600 은 사실상 제목 전용이고 700 도 제목이 주다.** 같은 크기·같은 역할에
굵기만 다른 자리가 계속 나왔다.

```
text-3xl 제목   푸터·공지사항 600   ↔   페이지 제목·교수초빙 700
text-xl  제목   게시물 상세  600   ↔   장학·교과목·세미나 목록 700
text-base 제목  학부소개·찾아오는길 600 ↔ 연락처·시설·진로 700
새소식 제목     메인 카드 600      ↔   목록 행 700          (같은 콘텐츠, 같은 크기)
```

메인 한 화면 안에서도 「공지사항」 600, 「새 소식」 500, 「바로가기」 500, 중요 공지 600 이었다.

**600 을 없애고 28곳을 700 으로 보냈다.** 남기는 쪽을 700 으로 고른 건 사이트의 모든 페이지 제목
(`PageTitle`)이 이미 700 이고, 렌더 기준으로도 700 이 600 의 세 배여서다.
규칙은 **400 본문 · 500 컨트롤(버튼·태그·메뉴·표 머리행·폼 라벨) · 700 제목·강조** 셋이다.

### 셋으로 줄인 근거는 다른 시스템에서 왔다

```
KRDS (같은 Pretendard)   400 · 700          "명확한 대비를 위해"
Carbon  (IBM Plex)       300 · 400 · 600    700 없음
Primer  (GitHub)         300 · 400 · 500 · 600   700 없음
Radix Themes             300 · 400 · 500 · 700   600 없음
USWDS                    "Most projects will use only 2-4 of these tokens"
```

**아무도 500·600·700 을 셋 다 쓰지 않는다.** 600 을 쓰면 700 이 없고, 700 을 쓰면 600 이 없다.
Atlassian 은 semibold 를 쓰되 *"fallback fonts don't support this weight and will default to bold"*
라고 경고한다.

### 목록 행의 제목은 700 이 아니라 500 이다

제목을 700 으로 모으고 나니 화면이 굵어 보였다. 재 보니 굵은 글자(600 이상)가 차지하는 비중이
**공지 목록 모바일 62% · 세미나 41% · 연구실 24% · 교과목 22%** 였다. 나머지 화면은 5~17% 다.

원인은 굵기가 아니라 분류였다. **목록 행의 제목을 「제목」으로 취급한 것.** 700 은 한 화면에
몇 개 없는 제목을 위한 굵기인데, 목록은 같은 것이 스무 번 반복되는 자리라 거기서는 강조가 아니라
배경이 된다. 특히 모바일에서 표가 카드로 접히면 첫 열이 화면 폭을 다 차지한다.

이 자리에 대한 선례가 이미 코드 안에 둘 있었다 — 공지 목록 데스크톱은 `sm:font-normal`(400),
진로 기업 표는 `font-medium`(500). 같은 「표의 첫 열」에 400·500·700 이 돌아다녔다.

**목록 행의 제목을 500 으로 내렸다**(`NoticeListRow`·`ResearchLabRow`·`CourseList`·`SeminarRow`·
`NewsListRow`·`SearchResultRow`). 공지 모바일 62%→13%, 세미나 41%→2%, 검색 14%→2%.

**고정 공지는 행 전체가 굵었다.** 핀 아이콘 + 주황 제목 + 행 전체 굵게, 신호가 세 겹이라
날짜·조회수까지 700 이었다. 행의 굵기만 걷고 제목은 남겼다 — 데스크톱에서는 제목이 주황이 아니라
`neutral-800` 이라(`text-main-orange sm:text-neutral-800`) 굵기까지 빼면 핀 아이콘 하나만 남는다.

### 「반복되는 항목의 제목」이 기준이다 — 목록이든 카드든

목록 행을 내리고 나니 그리드·캐러셀 카드와 어긋났다. **같은 콘텐츠가 자리에 따라 갈렸다** —
새소식이 메인 카드에서는 700, 목록 행에서는 500. 교과목도 카드형 700, 목록형 500.
600 을 없앤 근거가 "같은 콘텐츠·같은 크기인데 굵기가 다르다"였는데 그걸 다시 만든 셈이었다.

**"목록이냐 카드냐"로는 선을 못 긋는다.** 공지 목록이 모바일에서 카드가 되듯 그 구분은 화면 폭에
따라 바뀐다. 기준은 **반복되느냐**다.

대상은 코드가 아니라 화면에서 뽑았다 — 23개 페이지를 데스크톱·모바일로 훑어 **같은 클래스가 한
페이지에 세 번 이상 나오면서 700 인 것**을 셌다.

```
16회  교수 이름            PeopleGrid
 8회  메인 중요 공지 제목    ImportantSection
 6회  시설 이름            FacilitiesList
 5회  메인 새소식 카드 제목  NewsCard
 5회  메인 바로가기 항목     LinkRow
```

여기에 토글 뒤라 스캔에 안 잡힌 `CourseCard`(카드형), 다이얼로그 안의 CSEREAL 파트 이름,
타임라인 항목 제목을 더해 10곳을 500 으로 내렸다.

**같은 스캔에 걸렸지만 남긴 것 둘은 「강조」다** — 검색어 하이라이트(15회)와 고정 공지 제목(4회).
반복되는 게 목적인 자리라 반복 횟수로 판단하지 않는다.

### 무엇이 「제목」인지가 문제였다

되짚어 보면 이 절의 세 결정은 굵기를 민 게 아니라 **분류를 고친 것**이다.

```
1. 제목은 700 하나로          600·700 로 갈려 있던 것을 합쳤다
2. 목록 행은 제목이 아니다      → 500
3. 카드도 반복되면 제목이 아니다  → 500
```

1번을 정하고 나서 **무엇이 제목인지**를 두 번 다시 판단했다. 순서가 반대였으면 더 짧았겠지만,
굵어진 화면을 보고서야 목록 행이 제목이 아니라는 게 드러났다.

### 자간은 앱의 76% 가 이미 0이었다

`tracking-wide`(0.025em) 50곳을 비롯해 61회가 흩어져 있었는데, 값이 0.02·0.025·0.029·0.031em
넷이었다. 14px 에서 0.26 / 0.35 / 0.4px — **글자당 0.1px 차이라 눈으로 구분이 안 된다.**
`tracking-[0.025rem]` 은 절대값이라 크기가 바뀌면 0.029em·0.031em 으로 제멋대로 움직였다.

렌더 기준으로 **1370개(76%)가 이미 0** 이었다. 나머지 24% 를 0 으로 맞춰 자간을 없앴다.
KRDS 가 같은 Pretendard 계열에서 본문·라벨·내비 전부 `letter-spacing: 0` 이고(Display·큰 Heading 만 1px),
한글 조판 관례도 0 또는 음수다 — 우리는 양수라 방향이 반대였다. 화면으로 확인해도 차이가 안 보였다.

자간을 없애면 글자가 **좁아지므로** `whitespace-nowrap` 셀이 넘칠 위험이 없다.
남긴 것은 하나 — 연구실 상세의 오각형 배지(`tracking-[-0.019em]`). 도형 폭에 맞추려 좁힌 값이다.

### 행간에는 스케일이 아예 없었다

`--text-*--line-height: initial` 여덟 줄과 전역 `line-height: 1.2`(주석: "피그마와 줄높이가 다른
문제 조정")가 최초 마이그레이션부터 있었다. **크기 유틸리티가 font-size 만 설정**해서, 명시하지
않은 모든 글자가 1.2 를 상속했다. 그래서 읽는 글마다 각자 `leading` 을 얹어 56회·18가지 배수가 됐다.

**전역 1.2 는 안티패턴이 아니다.** 무단위라 상속이 안전하고(배수가 내려가 자식이 제 크기로 다시
계산한다), 값도 Pretendard 의 `normal`(1.14~1.21)과 거의 같다 — 걷어내면 오히려 좁아진다.
고쳐야 할 것은 전역이 아니라 **짝짓기가 꺼져 있다는 것**이었다.
Carbon·Radix·Material·KRDS·Tailwind 가 전부 크기와 행간을 한 쌍으로 준다.

### 크기마다 행간을 짝짓고, 값은 우리 사용에서 뽑았다

```
12·13·14·16px   1.35        18·20·24·30px   1.2
```

Tailwind 기본값(1.33/1.43/1.5/1.56/1.4/1.33/1.2)을 베끼지 않았다. 그 비율은 **행간을 4px 격자에
맞춘 부산물**이다 — `lg`(18px)와 `xl`(20px)이 똑같이 28px 를 써서 1.56 → 1.4 로 떨어진다.
우리는 베이스라인 그리드를 안 쓰므로 그 출렁임을 물려받을 이유가 없다.

값은 실측에서 나왔다. **크기별로 두 줄 이상 감기는 비율**을 `Range.getClientRects()` 로 셌다:

```
12px  7%    13px  2%    14px 11%    16px 28%    18px 0%    20px 0%    24px 4%    30px 5%
```

- **18·20px 은 한 번도 안 감긴다** → 1.2(지금과 같아 픽셀 무변)
- **16px 이 가장 많이 감기는데 그게 전부 목록·카드 제목이다.** 16px 을 본문으로 쓰는 곳은 안 감긴다.
  Carbon·Radix·KRDS 가 16px 에 1.5 를 주는 건 **그들의 body 가 16px 이기 때문**이고,
  우리 body 는 13~14px 이다(게시물 본문이 suneditor 에서 14px). 그대로 옮기면 틀린다.
- **14px 에 1.5 를 줘도 혜택받을 글이 두 곳뿐**이다 — 읽는 글은 이미 전부 `leading` 명시가 있다.
  1.5 는 읽기를 개선하는 게 아니라 라벨·날짜·표 셀의 상자만 키운다(모바일 +7~9%가 그거였다).
- 1.35 는 Butterick 범위(*"between 120% and 145%"*) 안이다.

실측 결과 데스크톱 +0~2%, 모바일 +0~5%.

### 명시된 행간 54곳 중 36곳은 행간이 아니었다

렌더에서 줄 수를 세어 보니 대부분이 **한 줄**이었다. 행간으로 상자 높이를 만들고 있었다.

```
Button.tsx      text-md px-[.875rem] py-[.3125rem] leading-6    14px 글자에 24px 행간 = 버튼 높이
CourseEditor    h-8 ... leading-[31px]                          32px 입력칸 안 세로 가운데 정렬
LeftNavMenuItem mb-6 block h-4.25 ... leading-5                 고정 높이 옆의 행간
제목 8곳         whitespace-nowrap ... leading-loose             안 감기는 제목의 아래 여백
```

**이건 패딩·높이 주제다.** 행간 규칙으로 정리하려 들면 계속 안 맞는다 — 손대지 않고 넘겼다.

진짜 읽는 글 15곳만 두 값으로 모았다 — **안내문·설명 상자는 `leading-loose`(2.0), 발췌·카드 설명은
`leading-normal`(1.5).** 이미 그렇게 갈려 있어서 네 곳만 바뀌었다(2.15·1.86×2 → 2.0, 1.6 → 1.5).
게시물 제목 3곳의 `leading-[1.4]`는 남겼다 — 20px 제목이 두 줄 될 때를 위한 분명한 역할이 있다.

### 획 굵기는 CSS 한 줄이 정한다

1.5 와 2 로 갈려 있었다. lucide 기본값이 2 인데 우리는 바꿀 때마다 `strokeWidth={1.5}` 를 손으로
붙여왔고, 안 붙인 17곳이 2 로 남아 **같은 줄에서 굵기가 달랐다**(페이지 이동 화살표 넷이 2, 옆의
클립·핀은 1.5). 다를 이유는 없었다.

값을 사용처마다 되풀이하는 대신 `app.css` 에 한 줄을 뒀다. lucide 가 모든 아이콘에 `.lucide` 를
달고, CSS 는 표현 속성(`stroke-width="2"`)을 이긴다. base 레이어라 개별 `stroke-*` 유틸리티는
그대로 이기고, 앞으로 추가되는 아이콘도 자동으로 맞는다. prop 47개를 지웠다.

```css
@layer base { .lucide { stroke-width: 1.5 } }
```

획은 viewBox 24 를 기준으로 그려지므로 아이콘을 키우면 획도 같이 두꺼워진다 — 16px 에서 1.0px,
24px 에서 1.5px. 글자가 커지면 획도 굵어지는 게 맞으니 그대로 둔다.

### 남은 것

- **굵기 스케일은 아직 안 닫혀 있다.** 색·크기와 달리 `--font-weight-*` 가 Tailwind 기본 9단계
  (thin~black) 그대로다. 실제로 쓰는 건 셋이라 닫을 수 있다.
- **제목 굵기를 통일하고도 500 인 섹션 제목이 둘 남았다.** 메인의 「새 소식」(데스크톱
  `sm:font-medium`)과 「바로가기」·「학부」(`LinkSection`). 같은 화면의 「공지사항」은 700 이다.
  셋 다 회색으로 눌러둔 자리라 굵기만 올리면 어색할 수 있어 색과 같이 봐야 한다.
- **`TimelineViewer` 의 「연도 추가」가 버튼 라벨인데 700 이다.** `ui/Button` 이 500 인데 안에서
  `font-bold` 로 덮는다. 버튼 인벤토리 건.
- **같은 폼 라벨에 500 과 700 이 섞여 있다.** `form/Fieldset` 의 legend 는 500,
  검색 라벨과 태그 legend(`SearchBox/Input`·`TagCheckboxes`)는 700 이다 — 셋 다 `text-md tracking-wide`.
- **`calendar.css` 가 굵기를 숫자로 직접 쓴다**(600·500·400). 색에서 잡았던 팔레트 이탈과 같은 모양이다.
- **행간으로 상자 높이를 만드는 곳이 36군데다.** `Button` 의 `leading-6`, `CourseEditor` 의
  `h-8 … leading-[31px]`, `whitespace-nowrap` 제목의 `leading-loose` 같은 것들. 전부 한 줄인데
  행간이 붙어 있다. **패딩·높이 주제로 넘겼다** — 버튼 높이 정책을 먼저 정해야 손댈 수 있다.
- **행간 스케일은 닫을 수 없다.** 색(`--color-*: initial`)·크기(`--text-*: initial`)와 달리
  `leading-<number>` 는 `--spacing` 에서 나온다 — `p-4`·`w-12`·`gap-2` 를 떠받치는 변수라 지울 수 없다.
  길이 문법이 항상 열려 있어서 막으려면 린트 규칙이어야 한다(임의값 `text-[15px]` 과 같은 자리).

## 아이콘

### 직접 만든 SVG 34개 중 20개가 아이콘이었고, 전부 lucide 로 바꿨다

앱에 두 벌이 섞여 있었다 — `lucide-react` 와 `?react` 로 불러오는 SVG 26곳. 같은 뜻을 둘이 따로
그리는 자리가 여럿이었다(위치·달력·사람·클립·검색·더하기·화살표). 남은 14개는 아이콘이 아니다 —
로고 6, 사이드바 눈금 2, 연구실 오각형 2, 메인 배경, 검색 결과 없음 일러스트, 첨부 상자의 클립,
그리고 유튜브.

**유튜브만 예외다.** lucide 는 브랜드 로고를 받지 않고([BRAND_LOGOS_STATEMENT.md](https://github.com/lucide-icons/lucide/blob/main/BRAND_LOGOS_STATEMENT.md)),
v1.0 에서 남아 있던 브랜드 아이콘을 전부 지우면서 Simple Icons 를 권한다. `lucide youtube` 로 바꿔두면
다음 메이저에서 사라진다.

### 죽은 파일 넷 — 중복 사본 셋과, 렌더된 적 없는 화살표 하나

`clip.svg`·`plus.svg`·`distance.svg`·`bookmark_icon.svg` 가 경로만 다른 사본으로 두 벌씩 있었다.

메인의 아래 화살표(`down_arrow.svg`)는 `hidden … sm:absolute` 라 **어느 폭에서도 안 보인다** —
`sm:absolute` 는 position 만 바꾸지 display 를 되돌리지 않는다. `sm:block` 을 빠뜨린 것으로 보이는데
지금 화면에서 그 자리가 비어 보이지 않아 되살리지 않고 지웠다(전용 `@keyframes arrowBounce` 도 같이).

### 크기는 옆 글자가 정한다 — 12 · 16 · 24

크기가 `h-[18px]`·`size-5`·`h-6 w-6`·`h-[30px]` 로 흩어져 있었고 같은 줄 안에서도 달랐다.

**16px 은 「기본」이 아니라 「본문 옆」이다.** Atlassian 의 16px 은 *"balances harmoniously with
body text"* 이고, Carbon 은 짝을 아예 규정한다 — *"16px and 20px icons are optimized to feel
balanced when paired with 14px and 16px IBM Plex. Use 24px and 32px when larger icons are
needed"*, *"Don't alter the icon-text size ratio"*. 그래서 고르는 기준을 글자 크기로 적는다.

```
size-3 (12px)   12px 글자 옆
size-4 (16px)   13·14·16px 글자 옆 — 기본
size-6 (24px)   20px 이상 제목 옆
```

전수조사(17개 페이지 × 데스크톱·모바일)에서 이 규칙을 벗어나는 건 **한 곳뿐이었다** — 연구 센터 제목이
데스크톱에서 24px 인데 옆의 링크가 16px 이었다(`sm:size-6` 으로 고쳤다). 13·14px 옆 228곳은 이미
비율이 1.14~1.23 로 Carbon 권고 안이다.

**아이콘 크기를 `1em` 으로 묶는 길은 접었다.** 14px 글자 옆 198곳이 16→14 로 줄어 Atlassian 이
"작으면 안 읽힌다"고 경고하는 구간으로 내려가고, 크기 스케일 여덟 단계를 아이콘이 그대로 물려받아
13·15px 같은 값이 생긴다. 이득 보는 곳은 하나인데 대가가 198곳이다.

예외는 아이콘이 아니라 그림인 것들이다 — 첨부 상자의 클립 48, 메인 「바로가기」의 화살표 30,
중요 공지 카드의 화살표 28, 검색 결과 없음 일러스트, 사이드바 눈금. 앞의 셋은 글 옆에 서는 게 아니라
상자나 행 전체를 여는 표시라 본문 크기를 따라갈 이유가 없다.

**첨부 상자의 클립은 SVG 를 그대로 둔다.** 그림자 필터가 얹힌 입체 그림이라 lucide 가 못 그린다 —
`Paperclip` 을 48px 으로 키우면 선만 굵어진 다른 그림이 된다.

**면적은 맞추지 않았다.** 「시각적으로 같아 보이려면 잉크 면적이 같아야 한다」는 말이 있어 재봤는데
lucide 자신이 아이콘마다 6배까지 차이 난다. 상자를 맞추는 게 이 계열의 관례다. 눈에 걸리던 건
면적이 아니라 **채움과 선이 섞인 것**이었고(우리 책갈피가 잉크 245, lucide 책갈피가 83), 그건 크기가
아니라 다음 항목이다.

### 원래 채워져 있던 넷은 채워 둔다

lucide 에는 채운 변형이 없지만 경로가 닫혀 있어 `fill="currentColor"` 를 주면 채워진다. 실루엣이던
고정글 핀·교과목 책갈피·캐러셀 재생·정지가 그대로 남았다. 나머지는 파일 안에서 `fill` 을 쓰긴 했어도
그린 모양이 선이었다 — Material Symbols 계열이 선 그림을 채운 경로로 내보내는 관례다. 그쪽은 선으로
두는 게 원래 모습이다.

### 상하 중앙이 안 맞던 곳 여섯

크기를 맞추자 정렬이 드러났다. 전부 **한 줄짜리 글 옆인데 `items-start` 이거나, 고정 높이 안에서
위로 붙어 있거나, `-translate-y-0.5`·`pt-0.5` 로 손으로 민 자리**였다. 증상이 셋이지만 고치는 법은
하나다 — 부모를 `items-center` 로 두고 손으로 민 값을 지운다.

측정은 스크립트로 했다. 아이콘 상자의 중앙과 **옆 글자 첫 줄 상자의 중앙**을 비교한다
(`Range.getClientRects()` — 상자 높이를 나누면 줄 수를 넘겨 센다). 지금 0.8px 넘게 벌어진 곳은
넷인데 전부 정상이다 — 제목이 두 줄이라 아이콘이 두 줄 전체의 가운데 있는 경우, 세로로 쓴 「더보기」,
절대 배치한 장식 클립, 그리고 0.9px.

### 색은 `currentColor` 로 받는다

SVG 29개가 색을 파일 안에 박고 있었다. 대부분 lucide 로 넘어가면서 없어졌고, 남은 것 중 눈금 둘과
오각형 둘을 `currentColor` 로 바꿨다. 연구 센터의 링크(`lucide Link`)는 `fill-neutral-500` 으로
칠하던 것이 `text-` 가 된다 — 선 아이콘이라 `fill` 이 더는 안 먹는다.

### 남은 것

- **그림 예외의 28 과 30 이 2px 차이다.** 중요 공지 카드의 화살표와 메인 「바로가기」의 화살표인데,
  역할이 같은데 값이 둘이다. 합치려면 어느 쪽이 맞는지 화면에서 봐야 한다.
- **`youtube_icon.svg` 만 `fill` 로 색을 받는다.** 나머지가 전부 `text-` 로 통일된 자리에 혼자 남았다.

## 문서

### 절마다 페이지를 준다

한 페이지가 19,214px(데스크톱 기준 19 화면)이 됐는데 목차가 없었다. 「컴포넌트 > 태그」를 보려면
12,506px 을 스크롤해야 했다. KRDS 는 색상·타이포그래피·아이콘·레이아웃을 각각 제 페이지로 두고
좌측 내비가 그 구조를 비춘다. Carbon·Atlassian 도 같다.

쪼갠 값은 URL 이다 — 「색 규칙 보고 와」를 링크로 가리킬 수 있다. 잃는 건 Cmd+F 로 전체를 훑던 것인데,
그건 `-content/` 의 MDX 를 직접 여는 쪽이 어차피 빠르다.

**좌측 내비는 두지 않는다.** 이동은 첫 화면의 목차와 절 끝의 이전·다음 링크가 맡는다. 절이 여덟이라
늘 붙어 있는 세로 목록이 본문보다 눈에 띄고, 좁은 화면에서는 머리글 아래 가로줄이 되어 본문을 밀어낸다.

목록은 `-nav.ts` 한 곳이고 첫 화면 목차와 이전·다음이 같은 배열을 본다. 경로를 조립하지 않고 그대로
적는 이유는 라우터가 타입으로 검사하게 두려는 것이다.

- ⚠️ **라우트 파일을 `component.tsx` 로 두면 안 된다.** TanStack 이 `component`·`loader`·
  `errorComponent` 같은 이름을 코드 분할 파일로 읽어 부모 라우트(`/design-system`)의 컴포넌트로
  붙여버린다. 그래서 `components.tsx` 다.
- **`__root` 의 앱 셸 차단이 정확히 일치를 보고 있었다.** `pathname === '/design-system'` 이라
  하위 절에서 푸터와 `sm:min-w-[1200px]` 이 되살아나 900px 아래에서 가로로 넘쳤다. 하위 경로까지
  보도록 고쳤다.
- **첫 블록의 여백을 지우는 규칙이 전체 폭 띠를 이긴다.** 본문 단의 `[&>:first-child]:mt-0` 과
  `[&>:not(h2):not(h3):not(p)]:mt-7` 이 자식의 `-mt-*` 보다 명시도가 높아, 머리글에 붙어야 할 회색 띠
  위에 72px 흰 틈이 남았다. 띠에 `data-bleed` 를 달아 두 규칙에서 빼고, 걷어낼 값은
  `--docs-gap-top` 한 곳에서 읽는다.
- **`max-[900px]` 는 900 에서 안 걸린다.** Tailwind v4 가 `width < 900px` 로 컴파일한다. 두 질의로
  갈라 쓰면 경계 폭에서 어느 쪽도 안 걸리는 구간이 생긴다 — 한쪽을 기본값으로 두고 다른 쪽만 덮는다.

## 패딩 · 간격

### 컨트롤 높이가 일곱 가지였다

한 줄에 놓고 재보니 이랬다.

```
25.55  버튼 sm        13px×1.35(17.55) + 패딩 4·4
34     버튼 md        leading-6(24)    + 패딩 5·5
36     버튼 md 테두리  위 + 테두리 2
37.59  버튼 lg        18px×1.2(21.6)   + 패딩 8·8
26     태그           h-[26px]
30.89  드롭다운        14px×1.2(16.8)   + 패딩 5·5 + 테두리 2
32     입력·날짜       h-8
```

높이를 만드는 방법이 셋이고(명시·행간·패딩), **테두리가 높이를 바꿨다** — 명시 높이가 없으면
`border-box` 가 소용없어서 같은 `size="md"` 인데 `secondary` 가 `primary` 보다 2px 컸다.

### 다른 시스템은 고정 높이를 안 쓴다 — `min-height` + 패딩이다

「32/40/48」로 알려진 Carbon 의 값은 사실 `min-block-size` 다. 패딩을 계산해 한 줄일 때 그 높이에
앉히고, 거기서 테두리 1px 을 뺀다(*"-1px to compensate for border width"*). Polaris 도
`min-height` + 간격 토큰이고, Primer 는 `min-height` 없이 `padding: 5px 16px; line-height: 20px`
로 32를 만든다 — **우리 `md` 의 `leading-6` + `py-[.3125rem]` 과 같은 모양이다.** 우리 방식이
틀린 게 아니라 바닥값과 테두리 보정이 없었다.

### 바닥값이 높이를 만들고, 패딩은 그보다 작게 둔다

```
min-h-7  (28)  태그 · 버튼 sm · 드롭다운 항목 · 파일 선택
min-h-8  (32)  버튼 md · 입력 · 드롭다운 · 날짜 · 검색 상자
min-h-10 (40)  버튼 lg
```

`box-sizing: border-box` 라 테두리가 바닥값 **안**에 들어간다 — 테두리 유무로 높이가 안 갈린다.
패딩 합이 바닥값보다 작으므로 한 줄에서는 항상 바닥값이 이기고, 글자가 두 줄이 되면 그대로 자란다.
Carbon 처럼 `calc()` 로 패딩을 맞추는 길도 있었지만, 그러면 6.55px 같은 값이 생긴다 — 격자에
올려야 하는 건 패딩이 아니라 바깥 높이라는 게 Carbon 의 입장이고, 우리는 둘 다 격자에 올리는
Primer 쪽을 골랐다. 그래서 컨트롤의 행간을 정수로 고정한다(`text-sm/4`·`text-md/5`·`text-lg/6`).

일곱 가지가 셋이 됐고, 임의값 `.3125rem`·`.875rem`·`.62rem`·`.625rem`·`0.37rem`·`h-[26px]`·
`h-7.5`·`leading-[31px]` 이 함께 사라졌다.

### 자작 pill 둘이 옛 버튼 클래스를 베끼고 있었다

교수진 필터가 `px-[.875rem] py-[.3125rem] leading-6` 을, 메인 공지 필터가 `py-[0.37rem]` 을
쓰고 있었다. 앞의 것은 `ui/Button` 의 md 클래스를 문자 그대로 복사한 것이라, 버튼을 고치면
조용히 어긋나는 자리였다. 둘 다 같은 바닥값으로 맞췄다.

### 여백 임의값 82회를 1회로 줄였다

두 번에 나눠 걷었다.

**하나 — rem 반올림 잔재 27곳.** Figma 가 픽셀을 소수점 둘째 자리 rem 으로 내보낸 값들이다
(`.62rem`=9.92 · `1.37rem`=21.92 · `2.19rem`=35.04 · `9.62rem`=153.92 …). 전부 앱이 이미 쓰는
값 근처라 가장 가까운 쪽으로 접었다 — 한 곳당 0.08~2.08px.

**픽셀 동일이 아니다.** 한 곳당 2px 이하지만 목록에서는 쌓인다 — 세미나 행의 19.2 → 20 은 행마다
1.6px 이라 페이지가 21px 길어진다. 나머지 페이지는 +2~6px 다.

**둘 — 스케일 값을 대괄호로 적은 54곳.** `pt-[60px]` = `pt-15`, `mx-[7.5rem]` = `mx-30` 처럼
값이 `--spacing` 배수로 정확히 떨어지는 것들이다. 수식상 항등이라 화면은 그대로다.

남은 임의값은 푸터의 `gap-[1ch]` 하나다 — 글자 한 칸 폭이라 픽셀 값으로 옮기면 뜻이 사라진다.

### 남은 것

- **값이 아직 56종이다.** 그중 23종이 **한 번씩만** 쓰인다(3·5·9·11·30·54·65·67·75·88·90·96·
  112·120·125·152·160·170·176·180·192·220·236). 큰 값은 대부분 메인 화면의 한 섹션 전용이라
  (`GraphicSection` 에만 67·75·125·170) 줄이려면 그 섹션의 세로 리듬을 먼저 정해야 한다.
- **4px 격자는 우리 규칙이 아니다.** 10px 이 65회, 26px 이 5회, 18px 이 5회 쓰인다. 실제 격자는
  2px 이고, `0.25`·`0.75` 단계도 이미 있다(3·11·13px). 격자를 4px 로 주장하려면 10px 65곳부터
  건드려야 한다.
- **텍스트형은 척도 밖이다.** `quiet`·`nav` variant 와 페이지 번호는 패딩이 없어 17.55·18.89px 다.
  상자가 아니라 글자라 바닥값을 주지 않았다. 다만 버튼 인벤토리에서 「텍스트형도 버튼인가」를
  정해야 한다.
- **CSEREAL 팝업의 버튼 둘이 46px 다.** `px-6 py-3` 짜리 자작 버튼이라 척도 어디에도 없다.
  `ImageModal` 과 함께 버튼 인벤토리 건이다.
- **WCAG 2.2 의 최소 대상 크기(24×24, AA)는 통과한다.** 18.89px 짜리가 있어 재봤는데
  간격 예외(지름 24 원이 다른 대상과 안 겹침)로 세 페이지 전수 실패 0건이었다.
- **레이아웃 치수는 아직이다.** 임의값 195종 중 컨트롤이 걷어낸 건 30회쯤이고, 나머지는
  `max-w-[30rem]`·`w-[432px]`·`pb-[150px]` 같은 치수다. `max-w` 는 스케일 7 / 임의값 33 으로
  거의 전부가 임의값이다.
- **rem 임의값에 반올림 무리가 남아 있다** — 13.92·21.92·26.08·35.04·153.92px. Figma 가 픽셀을
  소수점 둘째 자리 rem 으로 내보낸 흔적이다.

## 레이아웃 그리드

전수조사(라우트 39개 × 1280·768·390)부터 하고 규칙을 세운 뒤 한꺼번에 적용했다. 앞의 주제들과
달리 「기존 값을 존중해 하나씩」이 아니라 **없는 규칙을 새로 만드는** 일이었다.

### 640~1199 가 통째로 잘려 있었다

`body` 의 `sm:min-w-[1200px]` 과 `sm`(640)이 맞물려, 태블릿과 작은 노트북 전 구간에서 가로
스크롤이 났다. 이 앱의 레이아웃은 모바일과 데스크톱 둘뿐이고 `sm:` 이 그 스위치인데(442곳),
데스크톱은 사이드바 100 + 왼쪽 거터 100 + 본문 + 오른쪽 거터를 요구해 1024 아래에서는 본문이
눌린다. `--breakpoint-sm` 을 64rem(1024)으로 옮기고 `min-w` 를 지웠다.

서브내비는 그보다 위(`xl`, 1280)에서만 보인다. **1024~1279 는 서브내비 없이 데스크톱을 쓴다** —
자리를 두 값으로 나누는 것보다 단순하고, 본문이 724 로 1280 의 720 과 사실상 같아 폭이 넘어갈 때
튀지 않는다.

### 모바일 레이아웃도 상한이 필요했다

데스크톱 전환점을 1024 로 올리자 **모바일 레이아웃이 1023 까지 늘어나는데 좌우 여백이 20px
그대로라** 넓은 화면에서 글이 가장자리에 붙었다. 모바일도 640 에서 멈추고 남는 공간을 좌우로
나눈다 — 768 에서 여백 64, 1023 에서 192 다.

### 가로 기준이 층마다 달랐다

```
         왼쪽                      오른쪽
헤더      60      →  100          60   →  100
제목     100      →  100         100   →  100
본문     100      →  100         360   →  서브내비가 있을 때만 360, 없으면 100
푸터      60      →  100          60   →  100
메인     120·124  →  100          24   →  100
```

`.page-gutter-x`(본문 칸)와 `.page-band-x`(헤더·제목·푸터처럼 화면 끝까지 가는 띠)가 같은 식을
쓴다. 서브내비 자리는 `PageLayout` 이 다는 `data-subnav` 로 켜지는데, **푸터는 `__root` 에 있어
그걸 모른다** — `body:has([data-subnav])` 로 덮었다. 기준 폭이 층마다 갈리면 넓은 화면에서
푸터가 본문과 130px 어긋난다.

### 본문 상한 1200, 읽는 글 상한 720

최대 폭이 없어 학부 소개의 한 줄이 1280 에서 75자, 1920 에서 138자였다. KRDS 가 최대 콘텐츠
1200px(1248 을 넘으면 고정), Carbon 이 1584px 다. 한글 환경이 같은 KRDS 를 따랐다.

**본문 칸과 읽는 글은 다른 값이다.** 1200 은 목록·표·카드 격자의 폭이고, 문단이 이어지는 글은
그 안에서 720(≈75자)에서 멈춘다 — 본문 칸만 넓히면 1200 에서 한 줄이 122자가 된다. 거는 곳은
`HTMLViewer` 하나뿐이다(긴 줄이 나오는 페이지가 전부 그 안이다). 지금 1280 의 본문 폭이 그대로
720 이라 좁은 화면에서는 달라지지 않는다.

### 상한을 넘기면 가운데, 배경은 자르지 않는다

남는 공간을 오른쪽에만 두면 2560 에서 1160px 이 빈다. 그렇다고 컨테이너째 잘라 가운데로 옮기면
**흰 면이 끊겨 페이지가 왼쪽으로 쏠려 보인다.** 배경은 화면 끝까지 두고 패딩만 키운다.

서브내비 자리를 늘 비워두는 안(나)도 검토했는데, 그러면 가운데 정렬을 해도 빈 360 이 덩어리 안에서
같이 끌려가 내용이 260px 왼쪽으로 치우친다. 서브내비가 없으면 자리를 두지 않는 쪽(가)을 골랐다.

```
1024 →  본문  724      1280 →  본문  720 (서브내비 360)
1760 →  본문 1200      2560 →  본문 1200, 왼쪽 630 / 오른쪽 630
```

### 열 간격은 두 배씩 — 16 · 32 · 64

12 · 28 · 36 · 64 네 가지였다. 화면에 놓고 보니 12→16, 28→32, 36→32 는 눈에 안 띄는데
**64→32 만 교수 격자를 3열에서 4열로 바꾼다**(카드가 144px 고정). 그래서 64 는 남겼다.

### 페이지 아래 여백은 부모가 갖는다

같은 `pb` 를 써도 결과가 150·178·190·222 로 갈렸다 — 마지막 요소가 제 마진을 들고 있어서다.
`.page-end` 가 아래 여백과 함께 `> :last-child { margin-bottom: 0 }` 을 건다.

- ⚠️ **그 규칙은 `@layer` 밖에 둬야 한다.** 카스케이드 레이어는 명시도를 이겨서,
  `@layer components` 안에 두면 마지막 자식의 유틸리티 `mb-10` 에 무조건 진다. 클래스를 두 번
  적어 명시도를 올려도 소용없다.
- `PageLayout` 이 서브내비를 `{children}` **앞**에 렌더한다 — 절대 배치라 자리는 그대로지만, 뒤에
  두면 `:last-child` 가 서브내비를 가리켜 본문 마지막 블록의 마진이 안 지워진다.

### 식은 하나, 쓰는 방식이 넷

메인은 `PageLayout` 을 안 쓰고 어두운 카드가 **면 자체로 안쪽에 들어가야** 해서 패딩으로는 안 된다.
같은 식을 네 가지로 노출한다.

```
.page-gutter-x    본문 칸 — 오른쪽에 서브내비 자리를 비운다
.page-band-x      헤더·제목·푸터 — 서브내비 위를 지나가는 띠라 오른쪽도 가장자리까지
.page-inset-x     마진으로 밀어 넣는 것 — 메인의 어두운 공지 카드
.page-band-start  왼쪽만 — 메인 새 소식은 캐러셀이 오른쪽으로 흘러나간다
```

### 글 옆 이미지도 같은 규칙이다

읽는 글을 720 으로 정해 놓고, 대표 이미지가 있는 글에서는 320 짜리 이미지를 그 안에 띄워
글 자리가 372(한 줄 24자)였다. 같은 페이지의 이미지 없는 문단은 49자다.

글을 720 으로 고정하고 이미지를 줄이지 않는다. 나란히 못 놓으면 이미지를 글 위로 내린다 —
배치가 바뀌어도 글 폭이 안 움직이는 게 요점이다. 글 최소를 480 으로 낮춰 더 일찍 나란히
놓는 안도 있었지만, 그러면 창을 넓히는데 글이 720 → 492 로 좁아진다.

⚠️ **기준은 본문 칸이 아니라 화면 폭이다.** 1280 에서 보조 탐색 자리를 비우느라 칸이
979 → 720 으로 떨어진다. 칸을 보는 컨테이너 쿼리로 짰더니 화면을 넓히는 동안
가로 → 세로 → 가로로 두 번 뒤집혔다. 전환점은 720 + 28 + 이미지가 칸에 들어가는 화면
폭이고(칸 = 화면 − 560), 이미지 폭마다 다르다(200→1508, 240→1548, 320→1628).

### 버튼에 상태를 넣고 초점 링을 하나로 모았다

`primary` 에 hover 가 없었다. 가장 강조하는 버튼인데 반응이 없고, 팔레트의
`main-orange-hover`·`-active` 를 쓰는 곳은 `ImageModal` 의 자작 버튼 둘뿐이었다 —
그 화면이 상태를 원해서 `Button` 을 안 쓴 것이다. 원인과 결과가 붙어 있었다.

- 채움은 hover 에서 밝아지고 누르면 어두워진다. 텍스트형(`quiet`·`nav`)은 표면이
  어두워서 방향이 뒤집힌다.
- **초점 링은 표면을 따른다** — 밝은 면 `neutral-800`(15:1), 어두운 면 흰색(18:1).
  링크 색(파랑)은 쓰지 않는다. 이 팔레트에서 파랑은 링크라는 뜻이다.
- 흩어져 있던 초점 값 셋(`main-orange-muted` · `neutral-700` · `link`·offset-4)을
  표면 기준 둘로 모았다. 문서 셸이 `a, button, input, textarea` 를 전부 잡고 있어
  고치지 않으면 **디자인 시스템 페이지 안에서만 버튼이 파란 링을 쓰는** 상태였다.
- 죽은 `size="xs"`(선언 0회)를 지웠다. `quiet` 주석의 「밝은 표면」도 틀려서 고쳤다 —
  쓰는 두 곳 모두 어두운 표면이다.

### 잘리는 상자 안에서는 초점 링을 안쪽에 그린다

「outline 은 `overflow: hidden` 에 안 잘린다」는 말이 돌지만 틀렸다. 메인 캐러셀 카드가
4~5px(화면 밖 카드는 258px) 잘리는 걸 쟀다. Chromium 이슈 41159941 로 올라와 있다.

부모를 안 건드리는 해법은 **간격을 음수로 주는 것**이다(Nic Chan, "Tips for Focus Styles"
의 "Dealing with `overflow: hidden`"). `overflow: clip` + `overflow-clip-margin` 으로
여유를 주는 길도 있지만 MDN 기준 "Limited availability — not Baseline" 이라 못 쓴다.

우선순위는 **상자에 여백 → 안 되면 안쪽 링**이다. 기본을 안쪽 링으로 바꾸지는 않았다 —
`Button` 105곳에서 잘리는 건 0건이고, 안쪽 링은 채움 색마다 대비가 달라져
(`neutral` 채움 위 `neutral-800` 은 1.46:1) 표면이 아니라 채움을 따라가야 한다.

### 자작 버튼은 `ImageModal` 하나만 남긴다

`<button>` 을 직접 쓰는 곳이 34군데였는데 대부분은 버튼이 아니다 — 카드 뒤집기·달력 칸·
캐러셀 점처럼 그냥 누를 수 있는 영역이고, 프리미티브(`ui/*`·`form/*`)가 제 마크업을 갖는
것도 정상이다. 「버튼처럼 생긴 자작」은 넷이었고 셋을 `Button` 으로 바꿨다.

```
NoticeEditor      태그 제안받기          → secondary sm
CalendarToolbar   SquareButton 넷        → secondary sm  (지역 컴포넌트 삭제)
form/TextList     추가·삭제              → secondary md  (지역 Button·bgColor 프롭 삭제)
```

**「구조만 바꾸고 모양은 그대로」는 불가능하다.** `Button` 으로 바꾸는 순간 12px 흰 바탕
4px 이 14px 회색 채움 1px 이 된다. 자작 제거와 모양 수용은 한 묶음이다. 대신 모서리를
나중에 바꾸기로 하면 그때는 `Button.tsx` 한 곳만 고치면 105곳이 따라온다 — 먼저 구조를
모으는 게 싼 이유다.

폭이 필요한 자리는 **격자 칸이 버튼을 늘린다**(`<div className="grid w-24">`). `Button` 에
폭 프롭을 넣지 않아도 된다.

⚠️ `ImageModal` 의 꽉 찬 버튼 둘은 **예외로 남긴다.** 모달 하단 풀블리드 바는 흔한
패턴이고, 여기 하나 때문에 `Button` 에 폭 프롭을 넣거나 디자인을 바꾸는 건 과하다.
`focus:outline-none` 으로 초점 링을 지우고 있던 것만 걷어내고 안쪽 링을 줬다.

### 버튼 모서리는 1px 로 둔다

자작 셋이 독립적으로 **4px 모서리**에 닿았고 앱 전체로도 4px 이 34회로 가장 많다.
공지 편집 한 화면에서 에디터 도구·태그 제안·날짜 선택이 전부 4px 인데 DS 버튼만 1px 이다.
그래도 **버튼은 1px 을 유지하기로 했다** — 각진 모서리가 이 사이트의 모양이다.

그래서 자작을 `Button` 으로 모은 쪽이 4px 에서 1px 로 바뀌었다(위 전후 이미지).

남은 것: 값이 `rounded-[.0625rem]` 이라는 임의값이다. 모서리 반경 팔레트를 닫을 때
토큰으로 올린다. 그때 정리할 목록은 이렇다.

```
4px   34회   rounded-sm(25) + 맨 rounded(9)   앱의 표준
full   8회   태그·알약
1px    3회   버튼 셋(primary·neutral·secondary)
2px    4회   rounded-xs
6·8·12·16px  각 1회  ← 단발 넷, 접을 대상
```

### 히어로는 줄이지 않고 배치를 바꾼다

히어로 행이 `[사이드바 끝, 화면 끝]` 전체를 거터 없이 쓰고 `justify-center` 였다. 1024 에서
슬로건이 주 메뉴에서 2px, 그래픽이 화면 오른쪽 끝에서 28px 떨어진 채였고, 1024 아래에서도
그래픽이 `w-[80%]` 라 본문 칸을 좌우로 40~90px 넘었다.

`.page-band-x` 로 헤더와 같은 선을 쓰게 했더니 1024 에서 가로 배치가 안 들어간다 —
슬로건 281 + 그래픽 416 + 거터 200 = 897 인데 본문 칸이 848 이다. 간격을 0 으로 해도 안 맞는다.

**그래픽을 줄이는 길(1024 에서 416→220)과 배치를 바꾸는 길 중 배치를 골랐다.** 줄이면
그래픽이 슬로건의 곁다리처럼 보인다. 가로 배치는 `xl`(1280) 부터고, 그 아래는 모바일
히어로를 그대로 쓴다 — 가운데 정렬까지 같아서 900 과 1024 가 같은 모양이다. 1279↔1280 에서
높이가 517→450 으로 바뀌는 건 감수한다.

### 띠 안쪽 여백은 카드 기준으로 잰다

띠가 있는 섹션에서 잉크끼리 재면 틀린다 — 띠의 안쪽 패딩까지 섹션 사이 간격으로 세게 된다.
면 기준으로 다시 재니 메인의 섹션 사이는 이미 `88 · 88 · 88` 이었고 히어로만 174 다.
어긋난 건 섹션 사이가 아니라 **띠 안쪽**이었다.

```
새 소식   위 72 / 카드 아래 104   →  64 / 64
공지      위 62 / 아래 48         →  64 / 64
```

- 새 소식의 104 는 캐러셀 표시를 카드에서 40 띄우고 띠 아래로 또 40 을 둬서 생겼다. 표시를
  카드에 붙이고(24) 띠 아래를 16 으로 줄여 **카드 기준** 64 를 만든다. 띠 패딩만 64 로 맞추면
  카드에서 띠 아래까지가 128 이 되어 아래가 비어 보인다.
- 공지의 62 는 정해진 값이 아니라 고정 높이 448 에서 콘텐츠와 아래 여백을 뺀 나머지였다.
  `sm:h-112` 를 걷어내고 내용이 높이를 정하게 한다(448→466). 본문이 흐름으로 돌아오므로
  `relative` 가 필요하다 — 배경 그림이 절대 배치라 없으면 그림 아래로 깔린다.

### 세로는 전수조사만 끝났다

세로 간격 선언 645건 중 크기대별 성격이 다르다.

```
미세 0~16    305건 15가지   0·4·8·12·16 이 232건. 이미 사다리다
중간 17~48   305건 11가지   20~48 이 297건(97%). 18·26·30 여덟 건만 밖
큰   49 이상  35건 15가지   건수보다 가지가 많다
```

큰 값의 역할은 셋으로 갈린다 — 블록 사이(50~72, 23건) · 섹션 사이(80~88, 6건) ·
화면 끝(150~170, 4건). `64 · 88 · 150` 으로 모으는 안을 세워 뒀다(이동 17건, 총 153px,
최대 한 곳 20px). **세 값 모두 그 역할에서 이미 제일 많이 쓰는 값이라 새로 만드는 값이 없다.**
아직 적용하지 않았다.

히어로 아래 174 도 남았다 — 섹션 사이에서 유일하게 88 에서 벗어난 자리다.

### 레이아웃 절은 읽는 글이 아니라 만지는 도식이다

폭 구간·읽는 글 폭·열 간격·세로 리듬을 표로 적어 보니 절 하나에 산문 803자에 도식 하나였다.
다른 절은 도식당 44~207자다. 값이 폭을 따라 변하는 규칙은 표로 적으면 독자가 머릿속에서
보간해야 한다 — 끌어서 바꾸게 하면 그 일을 화면이 대신한다.

`WidthRuler` 는 `.page-gutter-x` 의 식을 그대로 옮겨 쓴다(`max(edge, (inner - block)/2 + edge)`).
실제 CSS 를 iframe 으로 불러오는 길도 있었지만 스타일시트 178KB 를 묶거나 nonce 를 손으로
옮겨야 해서 접었다. 대신 1024·1280·1760·1920 네 지점을 실측치와 맞춰 두었다.

`ReadingWidth` 는 줄 수를 `Range.getClientRects()` 로 센다. 한글·숫자·공백이 섞여 글자 폭이
일정하지 않아 나누기로는 안 나온다. 720 에서 한 줄 49자, 1200 에서 74자다.

**왼쪽 선만 넷이 공유한다.** 서브내비 자리를 비우는 건 본문뿐이다 — 띠까지 360 에서 멈추면
검색바가 안쪽에 어정쩡하게 선다. 다만 `--block` 은 넷이 같아야 한다. 층마다 다르면 넓은
화면에서 가운데 정렬 위치가 갈린다.

메인은 사이드바가 176(다른 페이지는 100)이라 시작점이 276 이지만, 「사이드바 + 100」이라는
규칙 자체는 같다.

### 남은 것

- **아래 여백이 아직 150~205 로 갈린다.** 선언은 전부 150 인데 남는 차이는 마진이 아니라
  **떠 있는 이미지(`float`)와 카드 안쪽 패딩**에서 온다(교수 상세 +32, 연구 센터 +28,
  시설 목록 +107). 그리드 규칙이 아니라 컴포넌트 건이다.
- **메인 캐러셀이 고정폭이다**(`w-[61.15rem] max-[1380px]:w-[45.35rem]`). 제목 칸에 `shrink-0`
  을 줘서 「새 소식」이 석 줄로 접히던 건 막았지만, 폭 자체는 여전히 임의값 둘이다.
- **그래픽 섹션이 자기 방식으로 가운데를 만든다**(`w-fit min-w-full` + `justify-center`).
  결과는 1200 으로 같지만 다른 섹션과 다른 길을 쓴다.

## 미결

- **SVG 자산 162회·CSS 파일 47회**가 팔레트와 같은 값을 하드코딩하고 있다. 값은 맞지만 토큰을
  바꿔도 안 따라온다. `?react` 로 불러오는 것은 `currentColor` 로 바꿀 여지가 있으나 아이콘마다
  의도가 달라 일괄 처리하면 깨진다.
- **그림자 투명도가 여섯 가지다**(0.05·0.07·0.15·0.2·0.25·0.3). 색이 아니라 그림자 체계 문제.
- **주황 상태색 3개가 `ImageModal` 하나만을 위해 있다.** `main-orange-hover`·`-active`·`-subtle`
  전부 그 컴포넌트 한 줄에서만 쓰인다. 그 모달의 버튼 둘은 `ui/Button` 을 안 쓰고 직접 만든 것이고,
  혼자만 완전한 hover·active 팔레트를 갖고 있다 — 반면 `ui/Button` 의 5개 variant 에는 active 가 없다
  (CLAUDE.md 가 "상태 없는 5개"라고 명시). **버튼 인벤토리를 할 때 여기를 다시 본다.**
- **어두운 면 위 글자를 세 단계로 정했다 — `white` · `neutral-300` · `neutral-400`.** 여섯 값으로
  흩어져 있었는데, 합치는 것보다 먼저 걸린 게 대비였다. `neutral-500` 은 어두운 면 어디에서도
  본문 기준(4.5)을 못 넘긴다 — 사이드바(`shell-100`)에서 **2.70** 으로 큰 글자 기준(3.0)마저 미달이다.
  그게 문서가 "나머지 메뉴의 색"이라고 가르치던 값이었다. 바닥을 `neutral-400`(5.07)으로 올렸다.
  밝은 면 위에서 `neutral-400` 이 "부수 정보"인 것과 역할이 겹치지만, 바탕이 반대라 밝기가 읽히는
  방향도 반대다.
  - `ui/Button` 의 `nav` 와 `quiet` 이 호버에서 반대로 움직이는 건(흰색→죽임 / `neutral-400`→밝힘)
    시작점이 달라서지 불일치가 아니다. 흰색은 더 밝아질 수 없다. 다만 `nav` 의 호버가 `neutral-200`
    이라 세 단계 어디에도 없어서 `neutral-300` 으로 맞췄다.
  - 보조 글자의 호버도 둘로 갈려 있었다 — `Dialog` 닫기는 `neutral-500→700`, `SelectionList` 는
    `500→800`. 본문 기본값이 `neutral-800` 이니 그쪽으로 합쳤다.
  - `NoticeEditor` 의 태그 제안 결과 문구가 `neutral-700` 이었다. 본문(800)도 보조 설명(500)도 아닌
    사이값이라 역할대로 `neutral-500` 으로 내렸다.
  - `SelectionList` 의 선택 항목은 주황 면 위에 `neutral-50` 이었다. 거의 흰색이지만 규칙은 `white`
    이므로 맞췄다.
- **어두운 쪽엔 진짜 계단이 없다 — `neutral-850` 과 `-800` 은 겹치지 않는다.** 해부도를 그리다 드러났다.
  `850` 은 카테고리 페이지의 제목 영역이고 그 **아래**에 `CategoryGrid` 가 다시 `neutral-900` 을 깐다.
  `800` 은 메인의 공지 카드로 `__root` 의 `neutral-900` 위에 앉는다. **둘 다 "페이지 위에 한 겹"이고
  서로 포개지는 일이 없다** — 같은 관계에 값이 둘인 셈이다(8/255 차이). 문서에는 각각 제 화면에서
  보여주고 역할도 「제목 영역」·「카드」로 따로 적었다. 한 그림에 위아래로 쌓아 그리면 없는 위계를
  지어내게 된다. **둘을 합칠지는 카테고리·메인 컴포넌트를 볼 때 판단한다.**
- **`neutral-50` 과 `neutral-100` 은 역할이 아니라 깊이로만 갈린다.** 문서에 "50은 영역, 100은 요소"
  같은 규칙을 적으려다 실제 사용처를 세어보고 접었다. Radix 는 2단계(영역)와 3단계(컨트롤)를 나누는데
  (*"Steps 3, 4, and 5 are designed for UI component backgrounds"*) 우리는 안 갈린다 — `neutral-100`
  42곳에 버튼 6·달력 셀 4(컨트롤)와 안내 상자 6·섹션 배경 4(영역)가 섞여 있고, `neutral-50` 도
  게시물 본문 영역과 입력란이 함께 있다. **같은 표 머리행이 `AdminTable` 은 50, `CourseList`·`labs`·
  `ConferenceListTable` 은 100 이다.** 그래서 문서는 Carbon 의 위치 어법(*"Container color on
  $background"*)만 쓴다 — 없는 규칙을 지어내지 않는다. 역할을 나누려면 코드를 먼저 갈라야 한다.
- **문서가 설명 못 하는 색이 20회 남아 있다.** 전수조사(앱 코드 552회) 결과 문서가 93% 를 덮고,
  남은 것은 규칙이 아니라 흩어진 값이다. 정리 대상이지 문서화 대상이 아니다.
  - 테두리 여덟 회를 하나씩 보니 넷은 규칙이었고 넷은 아니었다. **어두운 면에도 선의 계단이 있다** —
    `neutral-800`(푸터 위 경계선)과 `neutral-400`(모바일 검색 입력 밑줄)이 밝은 면의
    `neutral-100`·`neutral-300` 에 **같은 역할의 짝**으로 대응한다. 둘 다 실사용이 한 곳씩뿐이라
    계단(가장 약하게 / 한 단계 세게)으로 묶으면 없는 위계가 생긴다 — 문서에는 밝은 쪽 짝을
    같이 적어 "어두운 화면에서는 같은 역할에 다른 값을 쓴다"로만 말한다. 나머지 넷은 테두리가 아니다:
    `Nodes` 의 `neutral-600` 은 장식선이라 「연결선과 노드」가 이미 "회색 선은 어두운 제목 영역에"라고
    말하고 있고, `Radio` 의 `checked:border-white` 는 경계가 아니라 주황 점 가운데의 흰 고리다
    (도넛 구멍 역할이라 배경색에 가깝다). `Dropdown` 의 `focus:border-neutral-400` 은 초점 표시다.
  - 면 여섯 회 중 하나는 규칙이었다. **`neutral-800` 은 어두운 틀(`neutral-900`) 위에 올라온 면이다** —
    앱 전체 바탕이 `__root` 에서 `neutral-900` 이고 메인 공지 카드가 그 위에 `neutral-800` 으로 앉는다.
    셸과 같은 원리(밝을수록 앞)라 문서에 행으로 넣었다. `NoticeSection` 의 비선택 필터 pill 도
    같은 `neutral-800` 인데, 그건 카드와 **같은 색**이라 사실상 면이 없는 것이다(주황 테두리만 보인다).
  - 나머지 넷은 면이 아니거나 한 곳짜리다. `PeopleBulletRow` 의 `neutral-950` 3px 점과
    `NewsCarousel` 의 `neutral-300` 인디케이터는 **면이 아니라 표시**다 — 글머리 기호와 페이지 점이라
    글자·컨트롤 쪽에 가깝다(글머리 점이 제 옆 글자보다 진한 건 따로 볼 만하다).
    `form/TextList` 의 `hover:bg-neutral-300` 은 CLAUDE.md 가 지적한 자작 버튼이고
    (`bg-neutral-50` 에서 `-300` 으로 뛴다 — 다른 버튼은 `100→200`), `CategoryGrid` 의 2단계 카드
    `neutral-400`·호버 `-500` 은 1단계 카드(`neutral-100`)보다 한 단계 죽여 깊이를 준 것이다.
    **둘 다 컴포넌트 인벤토리 건이다.**
- **문서의 색 설명 어휘는 다른 디자인 시스템을 읽고 맞췄다.** 내가 지어낸 "계단"·"막" 같은 말을 쓰고 있었다.
  - **겹침이 색을 바꾼다**는 게 보편 규칙이고, 방향까지 같다. Carbon: *"In the light themes, layers alternate
    between White and Gray 10 with each added layer. In the dark themes, layers become one step lighter with
    each added layer."* KRDS 도 같다 — *"어두운 배경에서는 밝은 배경과 다르게 면의 깊이에 따라 레이어 배경면은
    점차 밝아지도록 표현한다."* 우리 규칙을 특별한 발견처럼 적을 게 아니라 이 문장 그대로 쓰면 된다.
  - **어두운 화면에서 왜 밝아지는지**는 Atlassian 이 빛으로 설명한다 — *"Imagine that the surfaces are
    distantly lit from the front — the higher the elevation, the lighter the surface looks."* 그대로 빌렸다.
  - **모달 뒤의 층에는 다들 고유한 이름을 준다** — Material `scrim`, Atlassian `blanket`, Polaris `backdrop`,
    Carbon·Radix `overlay`. 설명은 덮는다(covers)와 시선을 모은다로 갈린다. 우리 토큰이 `overlay` 라
    「오버레이」로 부르고 Toss 의 어법을 따랐다(*"Modal 컴포넌트 뒤에 보이는 배경으로 사용자가 콘텐츠에
    담긴 내용에 집중하는 것을 도와줘요"*).
  - 쌓이는 축에 이름 붙이는 방식은 셋이다 — 서수(Carbon `layer-01/02`), 강조도(Material `container-low/high`,
    Polaris `secondary/tertiary`), 물리적 역할(Atlassian `sunken/raised/overlay`). 우리는 서수(`neutral-50/100/200`)
    라 **이름이 역할을 말해주지 않는다.** 그래서 설명이 그 몫을 져야 한다.
- **`form/Radio` 가 `#ff6914` 를 임의값으로 박고 있었다.** `shadow-[0_0_0_1.3px_#ff6914]` — 대괄호
  **안쪽**이라 `text-[#...]` 만 찾던 검사에 안 걸렸다. `var(--color-main-orange)` 로 바꿨다.
  다시 훑으니 대괄호 안에 색이 든 클래스는 일곱인데 나머지 여섯은 전부 그림자의 검정·흰색 투명도다.
- **초점 링 색이 정해져 있지 않다.** `form/Dropdown` 의 항목은 `focus:border-neutral-400` 인데
  `focus-visible` 이 아니라 마우스로 눌러도 뜬다. 앱에서 `outline-*` 을 명시하는 곳은 둘뿐이고
  (`faculty` 는 `neutral-700`, `NoticeSection` 은 `main-orange-muted`) 나머지는 브라우저 기본값이다.
  디자인 시스템 문서 자신은 `outline-link` 를 쓴다. 셋이 다르다.
- **밝은 주황 위의 흰 글자는 기준 미달인 채로 둔다.** `main-orange` 위 흰색은 2.88 이고,
  `neutral-950` 으로 바꾸면 6.87 이 나온다. 실제로 바꿔보고 되돌렸다 — 주황 버튼이 검은 글씨가 되면서
  생김새가 너무 달라진다는 판단이었다. 주황을 어둡게 해서 흰 글자를 살리는 길도 있지만 그건
  공과대학에서 이어받은 브랜드색을 버리는 일이다. **대비와 브랜드 표현이 정면으로 부딪히는 자리이고,
  여기서는 브랜드를 골랐다.**
  - 대신 규칙을 면 기준으로 정리했다 — **`main-orange` 에는 흰 글자, `main-orange-muted` 에는
    `neutral-950`.** 밝은 주황은 컨트롤의 짧은 라벨(버튼·태그)에, 진한 주황은 읽는 글이 올라가는
    넓은 면(`ImportantSection`·`NoticeSection`)에 쓰고 있어서 이미 그렇게 갈려 있었다.
  - `CategoryGrid` 만 진한 주황 위에 `neutral-800`(4.16)이라 `neutral-950`(5.44)으로 맞췄다.
    그 카드의 글자색은 배경과 무관하게 고정이라 회색 배경에서도 한 단계 진해지는데, 대비는 오르기만 한다.
  - `CalendarColumn` 의 예약 블록은 `bg-main-orange/80` 이라 면이 밝아져 물려받은 `neutral-800` 으로도
    6.34 가 나온다. 규칙의 두 갈래 어디에도 안 들어가지만 통과한다.
- **임의값 문법(`text-[#f5f5f5]`)은 팔레트를 닫아도 통과한다.** 지금 앱 코드엔 0곳이지만 막으려면
  린트 규칙이 필요하다.
- **`ui/Button` 의 `secondary` 가 86회 중 45회다.** 보조 버튼이 기본값처럼 쓰이고 있어 강조 위계가
  실제로 작동하는지 의심스럽다 — 버튼 인벤토리의 출발점.
- **`calendar.css` 의 팔레트 이탈을 없앴다.** `--rdp-accent-color: #e65817` 은 토큰 참조로 바꾸고,
  `--rdp-accent-background-color: #fff5f0` 은 지웠다 — 팔레트 밖의 유일한 색이었는데
  react-day-picker 가 그 값을 범위 선택에만 쓰고 우리는 `mode="single"` 이라 화면에 나온 적이 없다.
- **색상 절이 360px 에서 5px 넘친다.** 스와치 오른쪽의 `code[ml-auto shrink-0 pl-3]` 이 줄지 않는다.
  절을 쪼개기 전부터 있던 것이다.
