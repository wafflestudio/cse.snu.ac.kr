# 처리 중 안내 위치 — PF-Q1

[HTML 비교 견본](pending-feedback.html) · [현재 DS](index.html) · [문구 방향](COPY.md) · [진행 현황](PLAN.md)

**판단 1개 · 앱 미적용.** 문구를 불필요하게 늘리지 않는 사용자 선호에 맞춰, 스피너나 긴 설명 없이 ‘저장 중… / 예약 중…’만 표시한다.

## 이미 정한 방향과 현재 구현

DS-005는 짧고 구체적인 행동명과 차분한 안내를 승인한 **방향**이다. 아래 앱 문구까지 적용됐다는 뜻은 아니다.

| 항목 | 현재 소스 | 이번 비교에서 사용하는 문구 |
| --- | --- | --- |
| 공지 작성·편집 | NoticeEditor는 둘 다 ‘게시하기’ | 편집 견본은 ‘저장 / Save’, 처리 중 ‘저장 중… / Saving…’. 작성은 적용 시 ‘게시 / Publish’와 구분 |
| 공용 Form.Action | 기본 ‘저장하기’, ‘취소’, ‘삭제’. 제출 중 버튼 비활성, 문구 그대로 | 실제 제출 상태가 연결된 사용처에 짧은 처리 중 안내 |
| 편집 취소·삭제 확인 | ‘편집중인 내용이 사라집니다.’ / ‘게시물을 삭제하시겠습니까?’. AlertDialog의 ‘취소 / 확인’ | 이번 비교에서 변경하지 않음. 문맥별 문구 연결은 별도 적용 작업 |
| 예약 추가 | ‘예약하기 / Reserve’, 제출 중 비활성. 취소 버튼은 유지 | ‘예약 / Reserve’, 처리 중 ‘예약 중… / Reserving…’ |

공지 편집의 한국어·영어 버튼은 **제안용 문구 견본**이다. NoticeEditor와 Form.Action의 현재 한국어 고정 문구가 이미 번역됐다는 뜻이 아니다. ‘저장’은 편집 화면의 행동을 짧게 표현한 견본이며 임시 저장 기능을 추가하지 않는다.

## 왜 지금 정하는가

Form.Action과 예약 추가는 실제 제출 상태로 버튼을 비활성화하지만, 문구만 보면 실행 전과 요청 중을 구분하기 어렵다. 기존 상태값에 짧은 안내를 연결하면 기다려야 하는 상태를 설명할 수 있다. 버튼의 기존 비활성 색·크기는 기준으로 유지하고 안내 위치만 비교한다.

| 안 | 표현 | 장점과 영향 |
| --- | --- | --- |
| **A 추천 — 버튼 안 문구 교체** | ‘저장’ → ‘저장 중…’, ‘예약’ → ‘예약 중…’ | 행동한 자리에서 상태를 확인하고 문구를 중복하지 않는다. 스피너 없음. 기존 버튼보다 줄지 않는 최소 폭을 확보해야 한다. 긴 한·영 문구는 더 넓어질 수 있다. |
| B — 버튼 옆 안내 | ‘저장 중…’ + ‘저장’ 버튼 | 행동명이 계속 보이지만 같은 행동을 두 번 읽게 된다. 좁은 예약창에서는 안내를 버튼 위 한 줄로 배치하는 견본이다. 스피너 없음. |

A의 최소 폭은 **현재 앱 버튼과 적용할 기본 행동명 중 넓은 폭**을 기준으로 한다. 이 견본은 보이지 않는 기준 문구로 폭을 확보하며, 공용 Button API 구현안을 확정한 것은 아니다. 모든 상태의 폭이 같다고 보장하지 않는다. 처리 중 문구가 더 길면 커질 수 있어 한·영 실제 앱 반영 후 이동·줄바꿈·넘침을 확인해야 한다.

## HTML 견본의 범위

[견본](pending-feedback.html)은 앱 Button md의 14px/24px, 좌우14px·위아래5px, neutral-700/white, secondary의 기존 색·테두리, disabled 40%를 옮긴 **HTML 재현이며 앱 캡처가 아니다**.

- 편집: 최소 검증 폭1200px 맥락의 하단 버튼 묶음을 원래 버튼 크기로 발췌한다. 1200px 전체 화면·입력 폼을 재현한 것은 아니다.
- 예약: 화면320px 안의90vw 모달(288px), 좌우28px 여백, 행동 영역232px을 재현한다. B는 이 폭에서 별도 안내 줄을 사용한다.
- 한국어·영어 모두 기본 상태와 A/B 처리 중 상태를 보여준다. 비교 문서는 작은 화면에서도 읽을 수 있게 구성하지만, 실제 앱의 반응형·요청 동작 검증을 대신하지 않는다.
- 예약의 취소 버튼은 현재 구현대로 처리 중에도 비활성화하지 않는다. 공지 Form.Action의 취소·삭제·실행은 현재 구현대로 모두 비활성 상태를 보여준다.

## 적용 경계와 남은 검증

[Form.Action](../../apps/web/src/components/form/Action.tsx)의 `formState.isSubmitting` 및 [예약 추가](../../apps/web/src/routes/$locale/reservations/-components/ReservationCalendar/AddReservationModal.tsx)의 `isSubmitting`처럼 **실제 제출 상태가 이미 연결된 곳만** 대상으로 한다. 공지의 `handleSubmit(onSubmit)`과 예약의 비동기 제출 연결을 소스에서 확인했다. 모든 Form.Action 호출부의 연결을 검증했다는 뜻은 아니다.

새 상태 관리·검증·제출·삭제·재시도 로직을 만들지 않는다. 처리 중 상태가 없는 곳, Sonner 내부, SunEditor와 CSP는 범위 밖이다. 성공 여부를 미리 단정하는 문구도 추가하지 않는다.

선택 후에는 해당 화면의 실제 상태 전환, 한·영 편집1200px·예약320px, 버튼 최소 폭·복귀·넘침을 확인한다. 현재는 소스 대조와 HTML 견본 작성까지이며 실제 앱 적용·렌더 검증은 남아 있다.

## 질문 PF-Q1

**처리 중 안내를 A처럼 버튼 안에서 짧게 바꿀까, B처럼 버튼 옆에 둘까?**

문구를 늘리지 않고 실행한 자리에서 상태를 보여주는 **A를 추천**한다. 이 질문은 안내 위치에 대한 선택이며, 모든 폼 문구나 새 처리 상태를 일괄 승인하는 질문은 아니다.
