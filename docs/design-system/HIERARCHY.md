# 정보 위계와 시각 표현의 역할 비교

[진행 현황](PLAN.md) · [화면과 두 안 비교](hierarchy.html) · [방향 초안](DIRECTION.md) · [결정 기록](DECISIONS.md)

2-2의 검토 자료다. DS-001~DS-003을 전제로 기존 화면과 코드의 역할을 비교했다.
**주요 실행은 A안(짙은 중립색 기본)으로 결정했다. [DS-004](DECISIONS.md).**
H-01~H-03은 기반·컴포넌트 검토에 사용할 역할 제안이며, 전체를 별도로 승인받은 것은 아니다. 앱과 기존 PNG는 변경하지 않았다.
이미지는 기존 캡처이고, 버튼 비교는 현재 값을 참고한 별도 HTML 견본이다. 픽셀 회귀 결과나 새 팔레트의 승인으로 취급하지 않는다.

## 1. 같은 ‘제목’도 서로 다른 질문에 답한다

| 화면 | 현재 위치·작업 | 대상·주요 내용 | 선택·보조 정보 | 제안하는 구분 |
| --- | --- | --- | --- | --- |
| 공지 상세 | 어두운 상단의 ‘공지사항’, 경로 | 밝은 본문 면의 게시물 제목과 본문 | 작성자·날짜·조회수, 태그, 이전 글·목록 | 구역 제목과 문서 제목의 역할을 구분. 문서 제목을 페이지 제목과 동일한 규칙으로 합치지 않기 |
| 연구 스트림 | 어두운 상단의 ‘연구·교육 스트림’ | ‘시스템 스트림’ 제목과 설명 | 주황의 선택된 항목, 연구실 링크, 오른쪽 보조 내비 | 구역 → 선택 → 선택 결과의 관계를 명시. 선택 표시는 실행 버튼과 구분 |
| 공지 작성 | 어두운 상단의 ‘공지사항 작성’ | 필드 라벨, 입력값, 본문 편집기 | 필수 표시·입력 예시·설정, 취소·게시하기 | 작업 제목 → 입력 묶음 → 완료 행동. 입력 예시는 라벨과 별도이며 보조 글자도 읽을 수 있어야 함 |
| 연구실 상세의 예외 | 상단에 개별 연구실 이름이 직접 나옴 | 연구실 소개 본문 | 접힌 모서리의 연락처 요약, 소속 스트림 링크 | 상단 제목이 항상 구역 이름이라는 규칙은 부적합. 대상 이름을 본문에 중복 추가할 필요는 없음 |

### 제안 H-01: 이름보다 역할을 먼저 정한다

- **현재 위치/작업:** 어디에 있으며 무슨 작업을 하는지 설명한다. 큰 어두운 면과 기존 제목 표현을 유지한다.
- **대상/읽는 내용:** 지금 읽거나 편집할 실제 대상을 식별한다. 본문과 설명은 읽기 흐름을 우선한다.
- **선택/탐색:** 현재 선택과 이동 가능한 대상을 구분한다. 선택된 상태와 키보드 초점은 별개다.
- **행동/상태:** 지금 실행할 일과 실행 결과를 설명한다. 선택·오류·비활성·처리 중을 같은 색의 변형으로만 정의하지 않는다.
- **보조 정보:** 날짜·작성자·입력 예시처럼 위계가 낮아도 필요한 정보는 충분히 읽을 수 있어야 한다.

역할마다 서로 다른 글자 크기가 반드시 필요한 것은 아니다. 같은 크기를 쓰더라도 굵기·간격·배경·위치로 구분할 수 있다.
이 역할 구분은 시각 설계를 위한 제안이며, 현재 DOM의 h2/h3 순서가 적절하다는 판정이 아니다.
구체적인 크기·행간은 본문 서체 연결과 지원 폭을 확인한 뒤 비교한다.

## 2. 주황과 기하학 표현은 한 가지 뜻으로 쓰이고 있지 않다

| 현재 표현 | 현재 사용처·의미 | 제안 H-02 |
| --- | --- | --- |
| 원·선·사선 | 페이지 제목 주변의 경로/구분, 보조 내비의 연결, 본문 섹션 구분 | 보존할 시각 언어로 정의. 선이 있다는 이유로 조작 가능하다고 해석시키지 않기 |
| 주황의 접힌 모서리 | 선택형 상세에서 현재 선택된 항목 | 선택 상태의 표현으로 설명. 다른 선택지의 링크 동작과 구분 |
| 어두운 접힌 모서리 | 연구실 상세의 연락처 요약 | 정보 묶음의 표현. ‘접힌 모서리 = 선택됨’이라는 전역 규칙을 만들지 않기 |
| 주황 글자·표시 | 현재 내비 항목, 태그, 필수 별표, 그래픽 | 각각의 역할과 배경을 구분. 작은 글자의 대비 문제는 별도로 해결 |
| 주황 버튼 | 일부 추가·예약·재시도뿐 아니라 공지 목록의 편집/완료 | 주요 행동의 원칙을 먼저 선택하고 사용처를 대조. 현재의 배치를 그대로 의미 규칙으로 승인하지 않기 |

## 3. 행동 강조의 실제 혼용

1-3에서는 primary를 주로 추가, neutral을 주로 저장·게시에서 관찰했다.
추가 대조 결과 같은 행동에도 두 variant가 쓰인다. **‘주황 = 추가, 짙은 회색 = 저장’은 현재의 일관된 규칙이 아니다.**

| 사용처 | 현재 표현 | 근거 |
| --- | --- | --- |
| 연구실 추가 | 주황 primary | [연구실 목록](../../apps/web/src/routes/$locale/research/labs/index.tsx) |
| 교수·직원 추가 | 짙은 회색 neutral | [교수 목록](../../apps/web/src/routes/$locale/people/faculty/index.tsx), [직원 목록](../../apps/web/src/routes/$locale/people/staff/index.tsx) |
| 공지 목록의 편집/완료 | 주황 primary | [AdminFeatures](../../apps/web/src/routes/$locale/community/notice/-components/AdminFeatures.tsx) |
| 같은 공지 목록의 새 게시글 | 짙은 회색 neutral | 위와 같은 사용처. 편집 모드에서는 비활성 |
| 폼 저장·게시 / 같은 묶음의 삭제 진입 | 둘 다 짙은 회색 neutral | [Form.Action](../../apps/web/src/components/form/Action.tsx). 삭제는 확인 대화상자를 여는 행동 |
| 예약 폼 제출 | 주황 primary | [AddReservationModal](../../apps/web/src/routes/$locale/reservations/-components/ReservationCalendar/AddReservationModal.tsx) |
| 게시물의 목록 이동 | 짙은 회색 neutral | [PostFooter](../../apps/web/src/routes/$locale/community/-components/PostFooter.tsx) |

이 표는 source의 현재 사용처를 대조한 것이다. 모든 로그인 화면과 상태를 새로 렌더한 결과는 아니다.

### 제안 H-03: 행동의 종류와 강조를 구분한다

먼저 한 작업 묶음 안에서 완료 행동·보조 행동·위험 행동의 관계를 정하고, 시각 variant를 대응시킨다.
일반 실행의 대표 예는 새 항목 시작·저장·게시·예약이다. 삭제는 파괴적 결과를 설명하고 확인하는 흐름으로 별도 검토한다.
‘한 화면에 강조 버튼은 무조건 하나’처럼 페이지 전체의 모든 독립 작업을 한 규칙에 묶지 않는다.

현재의 저장/삭제 동등 강조와 목록/완료 행동의 혼용도 이후 컴포넌트 단계에서 대조한다.
HTML 비교에는 위험 행동이나 부수적인 링크의 새 색을 제안하지 않았다.

## 결정한 선택 H-Q1 — A안, DS-004

검토 질문은 **일반적인 주요 실행 버튼의 기본 강조는 무엇으로 할까?**였다.
사용자는 “A 좋아”라고 답했다. 아래에는 선택 이유와 비교했던 대안을 보존한다.
장식·선택의 주황과 어두운 큰 면은 두 안 모두 유지한다. 이 질문은 주황을 없앨지의 재질문이 아니다.

| 안 | 주요 실행 | 장점 | 변화와 한계 |
| --- | --- | --- | --- |
| A. 짙은 중립색을 기본으로 — 권장 | 추가·저장·게시·예약 같은 주요 실행을 짙은 중립색으로 정리 | 현재 폼의 차분한 인상을 이어가고 주황의 선택·그래픽이 더 구별됨. 밝은 작업 면에서 행동의 대비를 확보하기 쉬움 | 기존 주황 추가·예약 버튼은 바뀜. 어두운 면 위의 행동은 배경에 맞는 별도 대비안이 필요 |
| B. 주황을 기본으로 | 같은 주요 실행을 주황으로 정리 | 과업을 실행할 버튼의 강조색을 명확하게 연결할 수 있음 | 현재 짙은 회색의 저장·게시·추가 버튼이 바뀜. 주황 사용 면적이 늘고 선택 표시와 공존함. 작은 글자 대비 보정 필요 |

[두 안을 바꿔 볼 수 있는 견본](hierarchy.html#actions)은 버튼 값과 문구를 고정하고 기본 강조색만 비교한다.
A안도 현재 화면을 그대로 보존하는 안은 아니다. 두 안 모두 목적에 맞게 사용처를 정리하는 제안이다.
현재 주황/흰색 조합의 대비 문제는 [기존 조사](ROLE-AUDIT.md)에 남아 있다. 견본은 현재 값을 이용한 강조 범위 비교이며
최종 색·호버·초점·위험 행동의 디자인은 이 선택 이후 다룬다.

기본 방향은 A로 정했다. 어두운 배경과 위험 행동 등의 예외는 구체적인 작업과 연결해 검토한다.
이 결정만으로 견본의 값을 최종 토큰으로 확정하거나 앱의 variant를 일괄 변경하지 않는다.

## 이 선택 뒤의 작업

H-Q1은 DS-004로 반영했다. 2-3의 실제 버튼·확인·오류 문구 비교는 [COPY.md](COPY.md)에 있다.
기반 규칙 단계에서는 서체 연결과 공개 배치, 역할별 색 조합을 실제 앱 화면에 적용한 비교를 준비한다.
기존 시각 회귀의 실패와 미수집 상태는 별도 항목으로 유지한다.

## 비교 자료의 검증

Playwright 1.57.0 Chromium 컨테이너에서 HTML을 로컬 HTTP로 열어 1280px·390px를 확인했다.
이미지 3장과 웹폰트 로드, 문서 자체의 가로 넘침 없음, 영역별 스크롤 이동, A/B 색과 안내 전환,
라디오의 키보드 전환을 확인했다. 작게 축소되어 이미지 전체가 보이는 경우에는 추가 스크롤이 필요하지 않다.
임시 검증 컨테이너는 저장소를 읽기 전용으로 연결했고 앱 서버·DB를 기동하거나 초기화하지 않았다.
이 검증은 비교 문서에 대한 것이며 앱의 동작·시각 회귀 검증을 대신하지 않는다.
