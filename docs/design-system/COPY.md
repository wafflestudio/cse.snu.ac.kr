# 행동과 결과가 드러나는 문구 — 검토안

[진행 현황](PLAN.md) · [방향 초안](DIRECTION.md) · [결정 기록](DECISIONS.md)

2-3의 문구 제안이다. **사용자 검토 전이며 앱에는 적용하지 않았다.**
현재 문구와 연결된 처리 코드를 대조했다. 아래 ‘현재’는 소스에서 확인한 문자열이며,
모든 오류·확인창을 브라우저에서 재현한 결과는 아니다. 작성자가 입력한 게시물 본문과 기관의
공식 명칭은 UI 문구 정리 대상과 구분한다. 이전 브랜치의 문구 규칙을 가져온 안이 아니다.

## 먼저 볼 세 가지 비교

| 문맥 | 현재 | 제안 | 달라지는 점 |
| --- | --- | --- | --- |
| 공지 작성 / 기존 공지 편집 | 둘 다 **게시하기** | 작성 **게시** / 편집 **변경사항 저장** | 새 게시와 기존 글의 갱신을 구분한다. 임시 저장 기능을 추가한다는 뜻은 아니다. |
| 수정 중 편집 취소 확인 | ‘편집중인 내용이 사라집니다.’ · **취소 / 확인** | ‘저장하지 않은 변경사항을 버리고 나가시겠습니까?’ · **계속 편집 / 나가기** | 편집을 계속하는 행동과 변경사항을 버리는 행동이 버튼에서도 드러난다. |

## 제안 W-01. 차분한 존댓말과 짧고 구체적인 행동명

- 설명·완료는 ‘~합니다 / ~했습니다’, 입력 안내는 ‘~해 주세요’로 쓴다.
  버튼에는 마침표 없이 ‘저장’, ‘게시’, ‘예약’, ‘연구실 추가’처럼 행동을 적는다.
- 대상이 분명하면 짧게 쓰고, 다른 대상·범위와 혼동되면 이름을 붙인다.
  ‘짧게’가 ‘항상 두 글자로’라는 뜻은 아니다. ‘변경사항 저장’, ‘반복 예약 전체 취소’도 가능하다.
- ‘확인’은 내용 확인 후 닫는 경우에 사용한다. 저장·삭제·이탈처럼 결과가 있는 행동은 그 결과를 적는다.
- ‘성공했습니다’보다 ‘무엇을 했습니다’를 쓴다. 같은 작업의 버튼·확인창·완료 안내에서 동사를 맞춘다.
- 문장에는 마침표를 쓰고 제목·라벨·버튼에는 생략한다. 처리 중 상태는 ‘저장 중…’처럼 표시하되,
  실제 요청 상태와 연결할 때 적용한다. 문구만으로 진행 상태를 꾸미지 않는다.

‘저장하기 / 게시하기 / 예약하기’를 유지하면서 의미만 정리하는 대안도 가능하다.
권장안은 ‘저장 / 게시 / 예약’이다. 현재 이미 쓰는 ‘삭제 / 편집 / 취소’와 형태를 맞추고,
행동을 구체화할 때 늘어나는 문구 길이도 줄일 수 있다. ‘~하세요’보다 ‘~해 주세요’를 안내의 기본으로 제안한다.

말투 통일을 이유로 중요한 결과나 주의사항을 삭제하지 않는다.

## 제안 W-09. 확인된 원인과 가능한 다음 행동만 안내한다

일괄적으로 모든 오류 뒤에 ‘다시 시도해 주세요’를 붙이지 않는다.
필수 입력·권한·대상 없음·통신 문제를 구분하고, 원인을 모르면 단정하지 않는다.
‘삭제한 내용은 복구할 수 없습니다’, ‘입력한 내용은 보관됩니다’도 실제 기능을 확인하기 전에는 추가하지 않는다.

| 사례 | 관찰과 처리 경계 |
| --- | --- |
| 저장 요청의 시간 초과 | 공통 apiErrorMessage는 ‘서버 응답이 늦습니다. 잠시 후 다시 시도해 주세요.’를 반환한다. 호출 작업이나 서버 반영 여부를 구분하지 않는다. 쓰기 요청에 ‘저장되지 않았습니다’라고 단정하거나 즉시 재전송을 권하는 새 문구는 보류한다. 결과 조회·중복 처리·입력 보존을 확인한 뒤 문구와 흐름을 함께 설계한다. 실제 중복 저장이 발생했다는 조사 결과는 아니다. |
| 검색 결과 추가 로드 실패 | 현재 ‘검색 결과를 더 불러오지 못했습니다.’가 표시되고 스크롤 이벤트로 재시도한다. **현재 없는 ‘다시 시도’ 버튼을 누르라고 안내하지 않는다.** 명시적 재시도 컨트롤이 필요한지는 피드백 패턴 검토에 남긴다. |
| 교과목 필수값 | 검증 message가 ‘교과목명’, ‘course name’처럼 항목명뿐이다. Form.Action의 오류 목록을 사용하지 않는 폼이므로, 문구 변경만으로 오류가 표시된다고 간주하지 않는다. 입력 오류 노출·초점 이동은 컴포넌트 단계에서 함께 검증한다. |

## 한국어·영어와 콘텐츠 경계

동일한 행동·결과를 두 언어에서 유지한다. 영어는 한국어 어미를 직역하지 않고 ‘Save changes’,
‘Publish’, ‘Reserve’, ‘Keep editing’, ‘Leave’처럼 쓴다. 예약 취소 ‘Cancel reservation’과
대화상자를 닫는 ‘Keep reservation’도 구분한다. 구체적인 영어 문구는 해당 사용처의 적용 비교에서 검토한다.

현재 번역은 [공통 사전](../../apps/web/src/translations.json),
[useLanguage](../../apps/web/src/hooks/useLanguage.ts)의 화면별 사전,
오류 사전으로 나뉘어 있다. Form.Action·AlertDialog는 일부 한국어 문자열을 직접 사용하며,
예약 상세는 설명을 번역하지만 완료 토스트는 한국어를 직접 사용한다.
공개 예약의 영어 흐름은 문구 적용 시 함께 확인한다. 관리 화면의 모바일 제외가 영어 제외를 뜻하지는 않는다.
UI 언어와 편집하는 콘텐츠의 한·영 선택도 별개다.

공식 학사 용어·학부 소개·게시물 본문을 새 말투로 일괄 고치지 않는다.
‘전공 이수 표준 형태’처럼 기존 메뉴 명칭이 긴 경우에도 먼저 명칭을 유지한다.

## 이번 판단 W-Q1

**짧은 행동명(저장·게시·예약)과 차분한 존댓말(~해 주세요 / ~했습니다)을 기본으로 하고,
버튼·확인·완료 문구에 실제 행동과 대상을 드러내는 방향으로 정할까?**

위 세 장면과 W-02~W-08은 이 방향을 적용했을 때의 구체적인 비교안이다.
승인되면 방향을 결정 기록에 남기고, 2-4에서 역할·예외를 정리한 뒤 기반 규칙으로 넘어간다.
새 API 기능·문서의 모든 예시 문장을 일괄 확정하는 질문은 아니다.

첫 기반 비교는 **본문 서체 연결**을 권장한다. 기존 조사에서 UI와 본문/에디터의 실제 서체가
다르게 확인됐고, 이를 먼저 해결해야 글줄·행간·간격의 후속 비교를 안정적으로 할 수 있다.
긴 공지와 데스크톱 편집을 기준으로 현재 상태와 등록된 Pretendard Variable 연결안을 비교하고,
메인의 Gowun Batang은 기존 정체성으로 유지하는 범위다. 아직 이 적용 비교는 시작하지 않았다.
