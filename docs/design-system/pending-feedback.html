처리 중 안내는 어디에 둘까?

PF-Q1 · 판단1개 · 앱 미적용
현재 DS 전체확정 방향과 앱 상태공지 편집예약320px답할 사항

HTML 비교 견본이며 앱 캡처가 아니다. 기존 버튼의 서체·색·패딩·비활성 농도를 옮겼다. 저장 요청을 실행하지 않는 정적인 견본이며 실제 앱 반영·상태 전환 검증은 남아 있다.

이미 정한 방향과 아직 적용하지 않은 것

  • DS-005 방향 확정: ‘저장·게시·예약’처럼 짧고 구체적으로 쓴다. 문구를 불필요하게 늘리지 않는다.
  • 현재 앱: 공지는 작성·편집 모두 ‘게시하기’, Form.Action 기본은 ‘저장하기’다. 공용 확인창도 아직 ‘취소 / 확인’, ‘게시물을 삭제하시겠습니까?’를 사용한다.
  • 현재 처리 중: 공용 폼과 예약은 실제 제출 상태로 실행 버튼을 비활성화하지만 버튼 문구는 바뀌지 않는다.

아래 기본 행동명도 제안용이다. 공지 편집은 ‘저장 / Save’, 예약은 ‘예약 / Reserve’로 짧게 표시한다. 영어 견본이 현재 공지 폼의 번역 완료를 뜻하지 않는다.

왜 이 표시가 필요한가

버튼이 흐려지는 것만으로는 요청 중인지 구분하기 어렵다. 이미 있는 제출 상태에 ‘저장 중… / 예약 중…’만 연결해 기다리는 상태를 설명한다. 두 안 모두 스피너와 긴 설명은 추가하지 않는다.

A 추천: 실행한 버튼 안에서 문구를 바꿔 같은 행동을 두 번 쓰지 않는다. B: 버튼 이름을 유지하고 안내를 옆에 둔다. 좁은 예약창에서는 안내가 버튼 위 한 줄을 사용한다.

A는 현재 버튼과 적용할 기본 행동명보다 작아지지 않는 최소 폭을 확보한다. 긴 한·영 처리 중 문구는 더 넓어질 수 있다. 견본의 폭 확보 방법은 앱 Button API 변경안이 아니다.

PF-Q1 · 하나만 정해 줘

처리 중 안내는 A 버튼 안 문구 교체 / B 버튼 옆 안내 중 어느 쪽이 좋을까?

문구를 늘리지 않고 실행한 자리에서 상태를 보여주는 A를 추천해.

실제 제출 상태가 이미 연결된 곳에만 적용한다. 새 처리 상태·제출·삭제·재시도 로직은 만들지 않는다. 예약 취소 버튼은 현재처럼 활성으로, 공지의 취소·삭제는 현재처럼 비활성으로 보여 준다. 승인 후 한·영 편집1200px·예약320px에서 실제 상태 전환과 폭을 확인한다.
